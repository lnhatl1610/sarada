# ADR 0013: Use the current two-level address catalog in Storefront

- Status: Accepted
- Context: Storefront checkout and saved customer addresses still require province/district/ward codes, while the current Vietnamese administrative model has province and commune/ward levels. ADR-0012 already adopted a dated official province/commune catalog for Admin; shipping rates continue to key off province codes.
- Options: (1) Keep requesting three-level codes or ask customers to type opaque codes, preserving the old payload but using obsolete administrative levels. (2) Reuse the official two-level catalog through public API endpoints, retain `district_code` as nullable legacy data, and preserve existing order/address snapshots.
- Decision: Use option 2 for new Storefront addresses. Publish the bundled General Statistics Office catalog through `GET /locations/provinces` and `GET /locations/provinces/{provinceCode}/wards`. The browser selects province then commune/ward; the API verifies the selected pair and resolves display names. New address rows and order snapshots use `province_code` and `ward_code` (the official commune code), with `district_code` null. Existing three-level payloads and historic district values remain readable and accepted during transition.
- Consequences: The catalog stays available offline and is cached publicly for one day. It is a dated snapshot (`2026-10-25`) and must be refreshed from the official source when the list changes. Customer shipping-rate calculation still uses the selected province. Admin and Storefront now import the same repository-level JSON file.
- Migration/rollback: A new migration makes `addresses.district_code` nullable without rewriting existing values. Rollback replaces null values with empty strings before restoring the non-null constraint; order JSON snapshots are unchanged.
