# Data Model

## Conventions
Use bigint identifiers; timestamps on mutable entities; soft-delete products, categories, and users; foreign keys and useful indexes. Money is integer VND, never float. Preserve applied migrations. Order items and shipping addresses are immutable snapshots. Every stock change is an inventory movement. JSON is reserved for snapshots/settings, not core relational data.

## Entity groups
- Identity: users (including email-verified `pending_approval` registrations and optional private body measurements for size suggestions), pending_email_changes (single-use hashed confirmation tokens; current email remains active until confirmation), staff_invitations (hashed one-time invite tokens with role, inviter, expiry and revocation state), roles/permissions, addresses, customer_notes (append-only internal notes with optional staff author), user_preferences (per-user appearance and notification choices), user_tasks (private or assigned admin tasks), two_factor_challenges (hashed, short-lived admin login challenges), refresh_tokens (hashed token, audience, expiry, and persistent-cookie choice carried across rotations), personal_access_tokens (short-lived JWT session references tagged `session`, plus scoped Sanctum admin API tokens tagged `api`; token hashes remain private, and API tokens record last-used time/IP).
- `users.phone_verified_at` records successful proof of control for the current customer phone. `pending_phone_changes` stores one per-user pending Vietnamese phone, only an HMAC of its six-digit SMS code, attempt count, request time, and ten-minute expiry. Confirmation atomically swaps the phone and timestamp; pending rows cascade when the user is deleted.
- Customer addresses use `label` (`home`, `company`, or `other`) plus independent `is_default` shipping and `is_default_billing` flags. Existing shipping defaults are backfilled as invoice defaults; server mutations keep one default address per purpose and select a fallback if a default address is deleted.
- `recently_viewed_products` stores up to 12 published product visits per customer, keyed by `(user_id, product_id)` with `viewed_at`; deleting the user or product cascades the rows. Storefront sync replaces the customer's list with a validated, most-recent-first set of public product slugs.
- `users.created_by` optionally references the staff account that created/invited an account; deletion of the creator clears this reference. Existing accounts and public self-registrations remain null until creation provenance is available.
- `users.avatar` stores an optional image URL up to 500 characters, matching the schema snapshot and media URL format.
- Catalog: categories, brands, collections/collection_product, products, product_images, product_videos, attributes, attribute_values, product_variants, size_guides, product_size_recommendations, tags/product_tag. Product videos are Admin-managed MP4/WebM files linked to a product, independently ordered, captioned, and optionally associated with one color. Product images can be flagged as ordered 360-degree frames and associated with a color; only flagged frames participate in the storefront viewer. Attribute names group color/size values; each size value belongs to a named size group. Product size recommendations store store-maintained height/weight ranges for the sizes actually sold on that product; storefront suggestions match only configured ranges and never infer body sizing from shipping weight.
- `store_locations` stores staff-managed physical store name, full address, validated current province and optional ward from the current Vietnam address catalog, public phone/email, opening-hours text, optional weekly JSON schedule, required coordinates, display order, and publication state. The schedule supports one same-day interval per weekday in `Asia/Ho_Chi_Minh`; public resources expose whether a scheduled store is currently open, while a null schedule means the status is unknown. The public directory exposes only active locations; visitor coordinates are used in-browser for nearby sorting and are not submitted to the API or persisted.
- `store_location_inventories` stores independent physical quantity, reserved quantity, and low-stock threshold for each `(store_location_id, variant_id)`. New balances start at zero; online inventory is never backfilled or treated as branch availability. `inventory_movements.store_location_id` attributes branch adjustment, reservation, sale, release, and return movements while `null` continues to identify the online pool.
- Orders store `fulfillment_type` (`delivery` by default), nullable `pickup_location_id`, and an immutable `pickup_location_snapshot`. Pickup orders have no shipping fee and use the selected branch stock pool; current status values are displayed with pickup-specific labels. The additive pickup migration is pending and has not been applied to the local schema snapshot.
- `faqs` stores topic-grouped questions and plain-text answers, with separate topic and entry ordering plus an active publication flag. Public reads include only active entries and search never returns draft text. `faq_helpful_votes` stores one yes/no response per FAQ and random browser UUID; votes cascade when an FAQ is deleted, and the UUID is not an authentication credential.
- `products.fit` stores an optional exact fit/silhouette value used by catalog filters. Public catalog filter options preserve the existing color-name list and add `color_swatches` with each color's optional `color_hex` for accessible Storefront swatches.
- Product sale windows are optional product-level start/end datetimes. Discount amounts remain on each variant (`price` below `compare_at_price`); when no window is set, existing discounts remain active indefinitely. During a scheduled window, storefront, cart, checkout, and manual order pricing use the variant discount; outside it they use the variant's comparison price. Order item prices remain immutable snapshots.
- Categories store optional description, image with accessible `image_alt` text, SEO title/description, parent, active state, and sibling order; existing rows receive a name-based fallback. Admin requires alt text whenever a category image is supplied. Category deletion is blocked while products or child categories still reference it.
- Brands store an optional uploaded logo and editorial banner (with accessible alt text), short story, and SEO title/description alongside name, slug, and active state. The public brand catalog only includes brands with published products.
- Collections store descriptions, SEO metadata, banner URLs with accessible `banner_alt` text, optional start/end timestamps, and `is_lookbook` for explicit homepage Lookbook selection. At most one currently published collection is featured; selecting another in Admin replaces the previous selection. The API requires a banner and alt text for a featured collection and rejects inactive or out-of-window collections. Existing rows default to not featured. Featured collection product pivots can store optional `lookbook_x`/`lookbook_y` coordinates from 0 to 100 percent; staff set them on the collection-products page, and `/lookbook/{slug}` renders keyboard-accessible product links at those image points. Existing products without coordinates remain in the product grid without a hotspot. The admin derives running/upcoming/expired/disabled status from the schedule and active flag.
- Stock: inventories, inventory_movements, inventory_adjustment_batches, and `product_stock_alerts` (pending normalized email or Vietnamese phone requests, unique per variant and contact method. Account restock subscriptions also retain the nullable customer owner and use that account's email; email contacts are deleted after notification queueing; phone contacts stay until SMS delivery succeeds and retry without putting the number into the queue payload. SMS uses Twilio only when configured).
- `product_price_alerts` stores one customer-owned product alert, its integer-VND reference price, active state, and notification timestamp. Enabling or re-enabling snapshots the lowest effective price among active variants. A scheduled command disables and queues one email after observing a lower price; customer/product deletion cascades the alert.
- `user_preferences.storefront_notifications` stores customer choices by event and channel. Order updates, price drops, and promotions can use email, the existing Laravel notification inbox, configured browser push, retryable Twilio SMS jobs that resolve the user's phone at send time, and Zalo ZBS Template Messages. Zalo credentials and approved template IDs are environment configuration; the rotated OAuth refresh token is encrypted in `settings` under `zalo_zbs_refresh_token`, and access tokens are cached until shortly before expiry. No separate preference table is required.
- Cart: carts, cart_items, wishlist_lists, wishlists. Each customer has a default wishlist and may keep additional named lists; wishlists links products to a list while retaining its owner for existing Admin customer/product summaries. Existing saved products are backfilled into a default list by an additive migration. Carts record the last item activity and nullable one-hour/24-hour recovery email claim timestamps; every add/update/remove or guest-cart merge resets both claims. Active signed-in customers receive reminders only when their email has an explicit newsletter subscription; guests can separately save an email and consent from a non-empty cart and withdraw it there. Only non-empty, unexpired carts are eligible; customer accounts must also remain active.
- Orders: orders, order_items, order_status_histories, order_change_requests, payments, payment_refunds, shipments. `orders.shipping_method_name` and `shipping_method_est_days` preserve the selected delivery method/estimate when the live method is later edited or removed. `orders.idempotency_key` is nullable and unique (up to 120 characters); `orders.idempotency_scope` stores a SHA-256 digest of the authenticated user ID or guest cart token so retries return an order only to the same caller scope. Legacy orders without a scope cannot be replayed by the storefront API. `orders.delivered_at` records successful delivery and anchors the seven-day inclusive customer return-request window. Optional VAT invoice requests snapshot `invoice_requested`, `invoice_tax_code`, `invoice_company_name`, and `invoice_address`; Admin order detail shows the customer-entered values. `order_change_requests` stores one pending customer cancellation/return request per order, its reason, staff decision, resolution note, and timestamps; requesters/reviewers are nullable references to users. The demo order seeder provides a pending cancellation request, a pending return request on a delivered order, and delivered orders with both pending and approved review examples.
- The connected local MySQL snapshot now has 83 tables and 795 columns. Blog tags, optional author fields, aggregate article detail views, weekly store schedules, catalog-backed store wards, and career opening listings are applied; seven unrelated pre-existing migrations remain pending, so do not infer that the local database is fully migrated from the latest timestamp alone. The snapshot also includes the activity-log index, `order_change_requests`, recently viewed/search tables, customer address/body measurements, restock and price alerts, shipping/payment/invoice snapshots, shipment tracking URLs, FAQ and review helpful votes, product Q&A, member and guest cart recovery tracking, store locations, review media type, current product metadata, explicit homepage Lookbook selection, optional product hotspot coordinates, editorial posts with product links/tags/authors/views, membership redemption fields, and promotion campaign delivery records.
- `career_openings` stores public job listing content and publication order. It has no applicant relation or CV storage; applications remain out of scope pending store policy.
- Migration `2026_11_05_230000_add_payment_instructions_to_orders_table` is applied to the connected local database; it stores the immutable bank details and transfer reference shown for a bank-transfer order. `fashion_store_schema.sql` is regenerated from that database and includes the nullable JSON column.
- Promotion/content: coupons, coupon_usages, banners, `storefront_promotion_campaigns`, `storefront_promotion_campaign_recipients`, pages (sanitized rich-text body and optional SEO title/description), FAQs, shipping_methods, shipping_rates, settings, reviews/review_images. Promotion campaigns queue channel-aware notices for active customer accounts and consented newsletter subscribers; temporary recipient rows use keyed email hashes for deduplication and are deleted when queue preparation finishes. Despite the legacy table name, `review_images` stores moderated review media with a `media_type` of image or video; submitted video stays private until the review is approved.
- Editorial: `blog_posts` stores the title, unique URL slug, free-form category name/slug, excerpt, optional author name and short bio, aggregate `view_count` (incremented by public detail requests without reader identifiers), accessible cover image, sanitized rich text, SEO metadata, publication state, and scheduled publication timestamp. Public reads require `is_published` and `published_at <= now`; article-to-product references use `blog_post_product`, ordered per post and cascading when either article or product is deleted. Categories are represented by normalized category values on posts so the Admin can create them inline without a separate category CRUD flow. Reusable editorial tags live in `blog_tags` and attach to posts through the `blog_post_tag` pivot.
- The `settings.home_sections` JSON value stores the twelve implemented P0/P1 homepage section keys in display order with an `enabled` flag. Older valid settings are normalized by appending newly supported keys; writes validate the complete unique key set and at least one enabled section. No new table is required (ADR-0017).
- Personalized recommendations derive category and brand affinity from the customer's recent published-product views and paid delivered/completed order items. The API returns only published, currently in-stock products and stores no extra profile or recommendation table.
- Marketing: `newsletter_subscriptions` stores one normalized email per address and the timestamp of the visitor's explicit newsletter consent. The store owner selected single-step opt-in: a valid, consented submission is subscribed immediately without an email-confirmation step. Duplicate submissions are ignored by the unique email constraint, and the public endpoint is rate-limited. A signed-in customer can also grant or withdraw this consent through the promotion-email setting; repeated opt-in does not reset the original timestamp. When Admin configures a currently usable welcome coupon, only a newly inserted subscriber receives its code; signed-in subscribers can also receive the welcome notice through enabled in-app, browser-push, and SMS channels. Duplicate requests never resend the welcome message.
- `newsletter_subscriptions.unsubscribed_at` and `unsubscribe_reason` retain the current opt-out state. Unsubscribe requests store only a unique SHA-256 token hash, a 30-minute expiry, and a pending reason on the existing normalized-email row; confirmed unsubscribe clears token data, and new explicit consent reactivates the row with a fresh consent timestamp. No email confirmation is used for initial signup.
- `storefront_promotion_campaigns` stores Admin-authored title/body/internal link and aggregate queue status. The temporary `storefront_promotion_campaign_recipients` table is unique by campaign and keyed email hash, tracks queued/skipped/failed preparation, and is cleared when queue preparation finishes. Admin sends require `coupons.manage`; actual notification channels follow each customer's saved preferences, while marketing email requires an active newsletter consent record.
- Search trends: `storefront_search_terms` aggregates exact published-product search matches by normalized term and UTC date using a SHA-256 uniqueness key. It stores no user ID or IP, skips email/URL/phone-like queries, exposes only terms with at least three submissions in seven days, and a daily scheduler prunes it to a 30-day retention window.
- Campaign banners store optional 500-character editorial descriptions, accessible image `alt` text, and an optional `video_url`; the image remains the poster and fallback. Storefront and admin banner APIs return the copy and same media reference and alt text, and campaign positions include the seeded hero, mobile hero, and campaign placements. `banners.show_countdown` enables a live Storefront countdown only for campaign placement and requires `ends_at`; the field defaults to false. Demo video files live under `api/public/demo-media/video/` and are seeded into the campaign banner record.
- `shipping_rates` contains unique province codes, display names, integer VND fees, optional province free-shipping thresholds, and an active flag. Admins manage rates from shipping settings; checkout uses the active matching row and otherwise falls back to global store settings. The storefront demo seeder creates missing sample rates for Hà Nội, Đà Nẵng, and Hồ Chí Minh using current global defaults; existing province rates are preserved.
- Review moderation stores an optional `moderation_reason` on hidden reviews. Review image counts and order references are exposed to authorized admin review details; removing reviews recalculates approved product rating totals.
- Reviews may store an optional public `store_response`, editable only by staff with review moderation permission after approval. Pending and rejected review responses are not exposed publicly. `review_helpful_votes` stores one vote per approved review and random browser visitor UUID; the UUID is not an authentication credential.
- `product_questions` stores customer questions tied to products, an optional staff answer, moderation status, and answer timestamps. Only answered questions for published products are public; resources expose the customer's display name but never contact data. Staff mutations require `reviews.moderate`; deleting the customer or product cascades the question, while deleting the answerer clears the staff reference.
- Demo catalog, Storefront media, order, and Admin workflow seeders run only in `local`/`testing`, including when invoked directly; this prevents AI-demo photos, sample inventory, customers, and orders from being added to production. `DatabaseSeeder` still installs the API roles/permissions and creates the configured super-admin account when credentials are supplied. Local/testing seeding attaches one AI-demo image to a pending review so the Admin review-image path has fixture coverage. Its alt text says it is not customer-submitted, and Storefront keeps the disclosure visible if the review is later approved.
- Operations: activity_logs, Laravel jobs/failed_jobs, and polymorphic notifications with per-admin read, archive, and snooze state. Admin activity logs default to 365 days of retention through `activity.retention_days`; `activitylog:prune` removes older rows daily using the `created_at` index. Read notifications older than 90 days are pruned daily. Supported single-record admin writes store redacted before/after snapshots for changed database fields alongside the submitted request payload; other audit entries retain their redacted request payload.
- Admin presence is stored in `users.presence_status`, optional `presence_until`, and `last_seen_at`. An available user with no recorded activity for 15 minutes is presented as away; an authenticated browser activity heartbeat refreshes `last_seen_at`, making the user available again. Busy, manually away, and hidden statuses remain user-selected until their optional expiry.
- Admin personal workspace: `user_tasks` stores a task assignee, optional assigning staff member, status, priority, due/reminder timestamps, recurrence, and an optional linked record. A scheduled command emits due reminders using each user's notification preferences; admins can list their own reminders and snooze them from `/me/reminders`, which resets `reminded_at` for the next scheduled delivery. `login_attempts` stores outcome and device/IP metadata for admin login history. The additive migrations also introduce `tasks.assign` for the `admin` and `super_admin` roles. Login history is retained for 180 days.
- Inventory import history: `import_jobs` records the submitting admin, source filename, status, row totals, and validation failures for CSV imports. Error rows are returned as a downloadable CSV only to the submitting admin or an admin with `exports.view_all`; raw source files are not retained.
- Personal performance uses `order_status_histories.changed_by`, `inventory_movements.created_by`, due/completion fields on `user_tasks`, and `activity_logs.user_id` for review approval attribution. No table change is required; review counts only include approvals logged after the attribution code is deployed.
- `staff.view_performance` is an additive permission granted to `admin` and `super_admin`; it may also be assigned to other roles through the role permission matrix. It does not add a data table.
- Admin onboarding progress: the `user_preferences` key `admin_onboarding` stores completed tour/checklist IDs and the dismissed flag. No new table is needed; the API accepts only the defined onboarding step IDs for admin audiences.
- Changelog read state: the `user_preferences` key `admin_changelog` stores the last app version viewed by each admin. The menu compares it with the configured `APP_VERSION` to show a new badge.
- Admin privacy and downloads: `export_jobs` tracks owner-scoped personal-data ZIPs, scheduled reports, and queued CSV exports for customers, products, orders, inventory, activity, and report sections. CSV exports keep the validated filters and format in job parameters, recheck the owner's active status and permission when the worker runs, and cap each owner at three active admin exports. Artifacts stay on the private local disk for seven days; failed or expired admin exports can be retried from the Downloads Center. Personal-data exports include an allowlist of profile fields, preferences, personal notes/tasks, own activity logs, and login history; credentials and authentication tokens are excluded.
- Scheduled reports: `report_schedules` stores an owner's report section, validated filters, CSV/PDF format, eligible staff recipients, local send time/timezone, recurrence, and next/last run state. The every-minute scheduler queues due jobs; generated files use the private local disk and seven-day `export_jobs` retention. Schedule management requires both `reports.view` and `reports.schedule`; recipients must be active staff with `reports.view`; schedules are owner-scoped.
- Personal-data ZIP generation requires PHP's `zip` extension and an active queue worker; scheduled expiry cleanup requires the Laravel scheduler.
- System health checks query the active database, configured queue and failed-job tables, mail transport configuration, local disk capacity/write access, and a scheduler heartbeat cached for three minutes. The detailed endpoint requires `system.health`; the account menu exposes only the overall status.
- System backups use Spatie Laravel Backup to create encrypted ZIPs containing the active database and `storage/app/public` media on a private local disk. `system_backup_runs` records the requesting admin, queued/running/completed/failed status, safe error text, archive metadata, and lifecycle timestamps. Only `system.backup` users can list runs or download archives; `BACKUP_ARCHIVE_PASSWORD` is required. A daily cleanup removes backups older than seven days, and system health warns when the last successful run is over 48 hours old. The permission migration grants `system.backup` to the default admin and super-admin roles.

## Important constraints
- Browser push uses the `laravel-notification-channels/webpush` package. `push_subscriptions` stores a polymorphic subscriber ID/type, unique browser endpoint, VAPID public/auth keys, content encoding, and device label, with an index for subscriber lookup. Subscription listing, test delivery, and revocation are scoped to the current admin; expired endpoints are pruned by the channel. Generate a stable VAPID key pair with `php artisan webpush:vapid` and configure `VAPID_SUBJECT`, `VAPID_PUBLIC_KEY`, and `VAPID_PRIVATE_KEY` in the runtime environment. Push requires HTTPS except on localhost and an active queue worker; replacing the key pair invalidates existing browser subscriptions.
- Unique users.email; nullable unique phone where DB semantics permit; unique slug/SKU/coupon code/order code.
- At most one pending email change per user; active pending addresses and token hashes are globally unique, and the raw token is never persisted.
- Trusted admin device tokens are unique SHA-256 hashes tied to one user and expire after 30 days; password or 2FA credential changes delete all of that user's trusted-device rows.
- Personal task reads and writes are scoped to the authenticated admin. A task may be assigned to another admin only when the actor has `tasks.assign`; completion updates `completed_at` with task status.
- Saved views are scoped to their owner unless `is_shared` is true; only the owner can update or delete a view. At most one default view per owner/page is maintained by transactional API writes.
- One inventory row per variant; nonnegative quantity/reserved and reserved ≤ quantity.
- Unique cart line `(cart_id, variant_id)`; unique wishlist `(user_id, product_id)`.
- One coupon usage per order; order code is opaque for public tracking.
- Payment refund rows are append-only integer VND records. Each refund belongs to one order/payment, requires a reason, and cannot exceed that payment's remaining refundable amount; payment and order status become `refunded` only after their captured amount is fully refunded. Customer order details expose the refund total and amount/timestamp entries while keeping staff-entered reasons private.
- Index product `(status, category_id)`, variant `product_id`, order `(user_id, created_at)` and `(status, created_at)`, inventory movement `(variant_id, created_at)`.
- Full-text index product name/short description where supported; use database-specific migrations carefully.
- Unique collection membership `(collection_id, product_id)` and wishlist membership `(user_id, product_id)`.
- Reviews are unique per user/order item when an order item is provided; rating is constrained to 1–5.
- Keep shipping method selection separate from province-based shipping rates; retain shipment tracking against the order. Shipments may store an optional HTTPS `tracking_url` configured by Admin. Guest tracking exposes it with the carrier and tracking code; do not infer carrier URLs from names or codes.
- Migration `2026_11_07_001700_add_tracking_url_to_shipments_table` adds the nullable URL. It is applied to the connected local database and included in the checked-in schema snapshot.
- Migration `2026_11_07_001800_create_faq_helpful_votes_table` stores one yes/no vote per active FAQ and random browser UUID, with a unique `(faq_id, visitor_id)` constraint and cascading FAQ deletion.
- New Admin and Storefront addresses use official province and commune/ward codes. Customer `addresses.district_code` is nullable for current addresses; preserve non-null historical values. New order snapshots store server-resolved `province_name` and `ward_name`, leave `district_code` null, and retain province-based shipping calculations. Admin and Storefront share the dated catalog from the General Statistics Office service; refresh it when the official list changes (ADR-0012/0013).
- Tags are shared records identified by a unique, normalized slug (`name` up to 50 characters, `slug` up to 80); `product_tag` uses a composite `(product_id, tag_id)` primary key and cascades when either parent is removed.

## SQL schema snapshot

Membership: `membership_transactions` is an append-only points ledger keyed by a unique reference. It records earned points, per-expiry-lot checkout redemptions, and refund/return adjustments per customer/order, integer VND earning basis, tier earning-rate snapshot, and expiration. Migration `2026_11_05_360000_create_membership_transactions_table` created the ledger; migration `2026_11_05_370000_add_checkout_membership_redemption` adds its source-lot reference and order redemption snapshots. The public `/membership/tiers` endpoint exposes the current program rules; the customer-scoped account API derives tier from paid delivered/completed spend in the trailing 12 months. Points are awarded once after delivery and payment, expire after 12 months, can be redeemed at checkout against the post-coupon merchandise subtotal, and are restored proportionally for refunds or in full for returns while preserving their original expiry. Voucher wallet remains unimplemented.
`fashion_store_schema.sql` is a schema-only snapshot of the connected local MySQL database. It contains 83 table definitions and 795 columns, including Laravel infrastructure tables, and contains no application rows. Generate it with `npm run export:schema-snapshot`; Laravel migrations remain the source of truth, and the SQL snapshot must not be executed against an existing database to apply changes.

Run `npm run audit:schema-snapshot` to compare the connected local database and this file. It checks table/column names, column types and nullability, and normalized full `CREATE TABLE` definitions (including defaults, indexes, foreign keys, and table options). - Product colors and sizes use `attributes` and `attribute_values`.
- Variant stock uses the dedicated `inventories` table so cart and checkout can lock stock rows independently.
- Multi-variant stock correction vouchers are stored in `inventory_adjustment_batches`; their ledger movements reference the voucher ID and are committed atomically.
- Payment returns are stored in `payment_refunds`; original payment amounts remain immutable, and refund reasons, amounts, recorder, and timestamps remain reviewable.
- User access is role/permission based; there is no single role enum on users. `users.must_change_password` marks admin accounts that reported an unfamiliar login session, were created/invited with an initial password, or signed in after their configured password age expired; the audience middleware blocks other admin requests until a password change clears the flag. `security.password_max_age_days` is owner-controlled, stored in `settings`, defaults to `0` (disabled), and uses `password_changed_at` (falling back to account creation time) to calculate expiration.
- Public registrations remain pending until email verification and an authorized administrator decision; invitation tokens are stored only as hashes and are single-use.
- Admin TOTP secrets are stored using Laravel's encrypted model casts; recovery codes are stored as password hashes. Login challenges store only token hashes.
- Money is stored as integer VND.
- The snapshot should be regenerated after applied schema migrations when a current SQL reference is needed.

## Snapshot and migration rules
On placement, copy product name, variant description/SKU/image/price, and shipping address onto the order. Do not recompute historic totals from current catalog rows. Add a new migration for every applied schema change; keep migration and this document aligned.

Migration `2026_11_06_203329_create_blog_tags_and_blog_post_tag_tables` adds normalized article tags; `2026_11_06_210104_add_author_fields_to_blog_posts_table` adds optional author name and bio; and `2026_11_06_211104_add_view_count_to_blog_posts_table` adds aggregate article detail views. All three are applied to the connected local MySQL database. Seven other pre-existing pending migrations are unrelated to this work.
