# API Conventions

- Prefix all routes with `/api/v1`; staff endpoints are under `/api/v1/admin`.
- Use plural kebab-case resource names, JSON, HTTPS in deployment, and explicit auth/audience/permission middleware.
- Success: `{ "data": ..., "meta": { "page": 1, "per_page": 20, "total": 0 } }` for paginated lists.
- Error: `{ "message": "...", "code": "STABLE_ERROR_CODE", "errors": { "field": ["..."] } }`.
- Use API Resources; do not serialize Eloquent models directly.
- Validate in Form Requests; whitelist filter/sort fields; cap pagination size.
- Storefront product-list `price_max` must be greater than or equal to `price_min` when both are supplied; invalid ranges return the standard 422 validation response.
- Storefront category slug `hang-moi` is the reserved new-arrivals collection and filters published products by `is_new`; other category slugs filter the active category tree, including descendants.
- Storefront product listings accept `target_gender=men|women|unisex|kids`, validated against the product's configured audience; category and audience filters can be combined.
- `GET /products/{slug}/related` returns only published same-category products and includes their active variants with current available inventory, so the Storefront can require an explicit in-stock variant for outfit suggestions. Variant prices and cart/order totals remain server-authoritative.
- Money values are integer VND; date/time values use ISO 8601 UTC.
- Storefront order details include customer-visible refund totals and amount/timestamp entries; refund reasons and recorder metadata are internal.
- Keep error codes stable (`OUT_OF_STOCK`, `COUPON_EXPIRED`, `INVALID_ORDER_TRANSITION`, `VALIDATION_ERROR`).
- `POST /orders` requires `Idempotency-Key`; retries return the original order response.
- Authentication uses Bearer access JWT; refresh via audience-specific httpOnly cookies. Storefront password login accepts the `identifier` field for email or phone; the legacy `email` field remains supported. Admin login remains email-only.
- Storefront login accepts optional `remember_me`; false sets a browser-session refresh cookie and true persists it for the configured session lifetime. The refresh-token record preserves that choice during rotation. Legacy clients that omit the field retain persistent-cookie behavior.
- Storefront customers cannot edit `phone` through `/account/profile`; `/account/phone/change` requires recent authentication and the current password, then `/account/phone/change/confirm` applies the phone only after a short-lived SMS code is verified. Phone login requires `users.phone_verified_at`.
- Public cart, checkout preview, and order-placement routes accept an optional storefront Bearer JWT. A valid storefront session uses the account's canonical cart and associates the order with that account; without a bearer token the request uses the guest cart token. Invalid or non-storefront bearer tokens fail instead of falling back to guest scope.
- `GET /auth/registration-status` is the public Storefront configuration source; expose only customer-safe store branding and contact details, maintenance, registration, SEO, and password-policy fields there. A GA4 measurement ID is public configuration; the storefront must not load its script or emit events until analytics consent is granted.
- `POST /contact/messages` accepts a rate-limited public contact request and optional validated image, then emails it to the configured support or store address without persisting the message or attachment. Contact details are public configuration only when intended for shoppers.
- `POST /products/{slug}/stock-alerts` accepts exactly one email or Vietnamese phone for an active sold-out variant of a published product. Phone alerts are available only when Twilio credentials are configured; the public registration-status payload exposes only that enabled/disabled state, never credentials.
- `GET /account/product-price-alerts` lists the signed-in customer's active price alerts. `PUT`/`DELETE /account/products/{product}/price-alert` enable/reset or disable the owner's alert; enabling snapshots the lowest effective price among active variants in integer VND. The scheduler queues one email only after observing a lower effective price. `POST /account/products/{product}/stock-alerts` subscribes the account email for one sold-out variant; all account alert endpoints require the storefront audience and scope records to the authenticated user.
- `POST /checkout/preview` accepts the selected `province_code`, optional `ward_code`, and optional active `shipping_method_id`; quotes return only currently eligible configured methods plus the province-rate fallback. Admin may scope methods nationally, by province, or to selected wards. Final `POST /orders` placement rechecks eligibility and locks the selected method, applies server-side free-shipping/coupon rules, and snapshots its name/estimate on the order.
- `GET /shipping/fee` accepts a valid `province_code` and optional `ward_code`, returning the province-rate fallback, active eligible methods, configured estimate text, and threshold. Fees are informational before cart/coupon calculation; checkout preview and placement remain authoritative.
- Authenticated `GET /account/vouchers` returns active public coupons and coupons previously used by that customer, with availability derived from current dates and usage limits. Coupons are not assigned to individual accounts; applying any code is revalidated against the live cart quote.
- Authenticated `GET /account/recommendations` derives product category/brand affinity from the customer's recent published-product views and paid delivered/completed orders. It excludes source products and returns only published products with available inventory; no interaction history returns an empty list.
- Storefront `GET /account/notifications` returns only the authenticated customer's own order, price-drop, and promotion notices. Individual and bulk read actions are also owner-scoped; events use Laravel's existing notification table.
- Storefront `GET/PUT /account/notification-preferences` reads and updates the customer's own event/channel choices in `user_preferences`. The API reports which channels are configured and rejects enabling unavailable channels; order and price-drop SMS requires an active Twilio configuration and a profile phone. Zalo requires credentials, all four approved event templates, and a profile phone. Browser push uses the same owner-scoped subscription records as Admin. Enabling promotion email creates an explicit newsletter consent record (without resetting an existing consent timestamp); disabling it withdraws that consent. Newsletter welcome coupons honor the subscriber's enabled in-app, browser-push, SMS, and Zalo channels.
- `/account/privacy/exports` and `/account/privacy/retention` are available to authenticated Admin and Storefront account audiences. Export jobs and signed downloads are scoped to the authenticated account owner; files expire after seven days.
- Zalo ZBS setup, template variable names, and credential rotation are documented in `docs/integrations/zalo-zbs.md`.
- Admin `GET/POST /admin/storefront-promotion-campaigns` requires `coupons.manage`. Sending queues a campaign for active customer accounts through their enabled promotion channels and sends email only where newsletter consent exists. Public links are rejected; temporary recipient rows are deleted after queue preparation.
- `GET /search/pages?q=...` searches published CMS pages and returns only safe titles, slugs, and text descriptions with bounded pagination; drafts and raw page HTML are never exposed.
- Storefront review resources expose the public display name but never account email; Admin review resources remain permission-protected and may include the customer email for moderation.
- `GET /products/{slug}/questions` returns only answered questions for published products; `POST` requires a signed-in Storefront customer. Admin question listing and answer/hide actions require `reviews.moderate`. Public resources never include customer contact details.
- API changes update `api/openapi.yaml` and generated FE types in the same change.
- Admin dashboard category revenue groups paid delivered/completed order items by the product's current category for the selected period; refunds are removed proportionally across order lines, matching product-performance reporting. Order items do not snapshot historical category, so reclassification affects older dashboard periods.
