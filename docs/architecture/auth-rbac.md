# Authentication and RBAC

## Token model
- Storefront password login accepts a normalized email address or the account's unique phone number. Admin login remains email-only. Legacy storefront requests using the `email` property continue to work; new clients send `identifier`.
- Access credential: signed 15-minute JWT with `aud` set to `admin` or `storefront`, sent as `Authorization: Bearer`; held in browser memory only. Its `sid` claim points to a revocable `personal_access_tokens` session row. The API checks that row and its audience ability on every protected request; the opaque Sanctum token value is never returned or accepted as a bearer credential.
- Cart, checkout preview, and order placement allow guest access but resolve an optional Bearer token when supplied. A valid storefront token binds the cart and order to that customer; malformed, expired, revoked, or admin-audience tokens are rejected and cannot silently fall back to guest scope.
- Refresh: 64-byte random opaque token, SHA-256 hash persisted with expiry, device/IP metadata, remembered-cookie choice, and revoked/replaced linkage; httpOnly Secure SameSite=Lax cookie. Storefront login defaults to a session cookie when `remember_me` is false; when true, the cookie persists for the owner-configured session lifetime (14 days by default). Older clients that omit `remember_me` keep the prior persistent-cookie behavior. The refresh-token row keeps this choice across rotations. A token family is the forward `replaced_by_id` chain that begins at one login-issued refresh token.
- Rotate on every refresh in a transaction. Reuse of a revoked token locks and revokes that token and every successor in its family, including any remaining access-session rows; unrelated browser/device sessions remain active. Logout revokes the current access and refresh credentials.
- Admin login history records success, incorrect password/2FA, and lockout outcomes without storing credentials. Entries are visible only to the matching admin account and are pruned after 180 days.
- Admin logout-all revokes every admin refresh/session row and trusted-device record for the current account; it does not place access credentials in browser storage.
- Reporting an unfamiliar admin session with `POST /account/sessions/{session}/report` revokes only that session and its refresh token, sends a mandatory security alert, and sets `users.must_change_password`. While the flag is set, admin API requests return HTTP 423 with `ADMIN_PASSWORD_CHANGE_REQUIRED`, except identity read, logout, account/session reads needed for recovery, sudo confirmation, and password change. A successful password change clears the flag and revokes other sessions by default. The account UI directs the admin to change the password and recommends enabling TOTP; API authorization remains authoritative.
- Sudo mode is cached for 10 minutes against the current admin JWT session row, so confirming one browser session does not authorize another. `POST /account/sudo` verifies the current password and, when enabled, a TOTP code; sensitive routes use `recent.auth`, and `GET /account/sudo` reports the current session's expiry. API token management uses this mode.
- `GET /admin/staff/{staff}/performance` requires `staff.view_performance` and limits access to assignable staff/admin targets. Order, inventory, and review sections additionally require the viewer's matching domain permission.
- Personal API tokens are separate Sanctum credentials tagged `token_type=api`, limited to the admin audience, and scoped to an explicit subset of the owner's current permissions. Routes accept these tokens only when they have an explicit `permission:` middleware gate; that middleware intersects the route permission with token abilities. Token management stays on the short-lived JWT session, allows at most 10 tokens per admin, and returns plaintext only once. Tokens expire after 7, 30, or 90 days by default; non-expiring tokens require the owner setting `security.allow_non_expiring_api_tokens`. List and audit data omit token hashes and plaintext.
- Separate audiences use distinct refresh cookie names and path scopes so admin and storefront sessions cannot collide.
- Personal data export routes accept either account audience through `account-audience`; each export job and download remains scoped to the current user ID.
- Local Admin and Storefront API defaults follow the hostname used to open each app, keeping refresh-cookie requests same-site for both `localhost` and `127.0.0.1`. When `VITE_API_URL` is configured separately, use a same-site origin; cross-site API origins are incompatible with the `SameSite=Lax` refresh cookie.
- An authenticated password change verifies the current password and requires the new password to differ. It keeps the current session active, revokes other access and refresh sessions by default (users can opt out in account security), and always removes remembered trusted-admin devices. Older clients that omit `logout_other_devices` retain the secure default. The account receives an email notice after the change.
- Owner setting `security.password_max_age_days` optionally expires admin passwords; `0` disables the policy. At admin session issuance, an expired password sets `users.must_change_password`, and audience middleware blocks protected requests until password change. Account-menu summary warns within 14 days of expiry. Directly created and invitation-created staff must change the initial password at first sign-in.
- Passwords set during registration, staff invitation acceptance, account changes, staff creation, and password recovery are checked against known breach data. The built-in Laravel uncompromised rule uses k-anonymity: only the first five SHA-1 hash characters are sent to the Pwned Passwords range API, never the password or full hash. The outbound request times out after five seconds; a matching breach rejects the submitted password with a Vietnamese validation error.

## Roles
System roles are `super_admin` (store owner), `admin`, `sales_manager`, `warehouse_staff`, `customer_service`, `content_editor`, `accountant`, and the retained legacy `staff` role. `customer` is limited to storefront account actions. The role presets map to API permissions: sales manages orders/customers/coupons/reports; warehouse manages inventory and reads product/order data; customer service reads customers and orders and moderates reviews; content editors manage banners and pages; accountants can read orders and reports. The `/roles` matrix is owner-editable, while the owner role's full permissions are protected from edits. Every admin role can authenticate to the admin audience; permissions still decide which API operations are available.

## Permission naming and enforcement
Use `resource.action`: `products.view/create/update/delete`, `orders.view/update_status/cancel`, `inventory.adjust`, `customers.view`, `coupons.view/manage`, `users.manage`, `staff.security`, `system.backup`, `reports.view`, and `reviews.moderate`. `customers.view` grants customer list/detail/export and global search; profile and status changes require `users.manage`. `staff.security` gates password-reset delivery, other staff session revocation, and 2FA resets. `system.backup` gates private backup metadata, queued archive creation, and authenticated downloads. `coupons.view` grants read-only coupon lists and usage history; mutations require `coupons.manage`. Map permissions to Laravel policies and route middleware. `/admin/auth/me` returns the current role/permissions. UI guards only improve UX; every API request is independently authorized.

## Browser and abuse controls
Use a single-flight refresh interceptor and retry each pending request at most once. Never persist access/refresh tokens in localStorage. Guest cart tokens are random, scoped to cart endpoints, and are not credentials. Rate-limit login to 5/minute per IP+email, checkout to 10/minute, public APIs to 60/minute by configured policy. Admin credentials also trigger a 15-minute lockout for the email/IP pair after five incorrect attempts; the `/locked` screen shows the remaining time. CORS allows only configured app origins; local defaults include `localhost` and `127.0.0.1` on Vite ports 5173–5175. API unauthenticated requests return JSON errors instead of redirecting to a web login route. Ensure cookie refresh endpoints have SameSite and origin/CSRF protections.

The admin SPA applies the shared refresh client to admin and account API requests. Concurrent 401 responses share one refresh call; each request retries once. If refresh fails or the retry is still unauthorized, keep the current route mounted and require the account password in a blocking reauthentication dialog. Accounts with 2FA must also complete a fresh TOTP or recovery-code challenge before the session is restored. Login and refresh requests are excluded from the interceptor to prevent recursive refresh attempts.

## Registration and staff invitations
Public customer registration is enabled by default only in `local`, `testing`, and `uat`; it is disabled in other environments unless the owner explicitly enables it. Registration requires terms acceptance, offers a separate optional marketing-email consent, creates an unverified `pending_approval` account, and sends a signed verification email without issuing a session. The newsletter subscription is created only when marketing consent is explicitly selected. Storefront login is blocked until the user verifies the address and an administrator approves the request. Approval assigns a role and sends a decision email; only `super_admin` may grant `admin`.

`StorefrontOrderDemoSeeder` creates the local demo customer and its order/address/review fixtures using `STORE_DEMO_CUSTOMER_EMAIL` and `STORE_DEMO_CUSTOMER_PASSWORD`. When the password is unset in `local` or `testing`, the seed uses the sample `StoreDemo123!`; outside those environments, configure a unique password before seeding. Never use the sample credential on a public or production environment, and do not seed demo accounts into production.

`AdminWorkflowDemoSeeder` creates a verified `demo.staff@example.test` account with the .staff. role only in local/testing environments. Its password is configured through `STORE_DEMO_STAFF_PASSWORD` (the development example is `StoreDemo123!`); replace the example secret for local use and never seed this account into production.

Email changes require the current password. The requested address and SHA-256 token hash are stored separately; the current email remains active until the single-use confirmation token is redeemed. Confirmation expires after one hour, marks the new email verified, and sends a security notice to the former address.

Customer phone changes require recent authentication, the current password, and a Twilio SMS code. Only an HMAC of the six-digit code is stored; codes expire in ten minutes, allow at most five attempts, and can be resent once per minute. The account phone is replaced only after confirmation, and storefront phone login is unavailable until the current phone has a `phone_verified_at` value.

Staff invitations store only a SHA-256 token hash, expire after 24, 48, or 168 hours, and are single-use. Resending revokes the prior token and issues a new one; administrators can revoke pending invitations. Accepting an invitation sets the account password and marks the invited email verified before activating the assigned system role. Only `super_admin` can assign the broad `admin` role.

## Admin two-factor authentication
Admin accounts may enroll an RFC 6238 TOTP authenticator after confirming their password. The pending secret is encrypted at rest and does not become active until a valid six-digit code is confirmed. Eight recovery codes are displayed once and only their password hashes are stored. Replacing recovery codes or disabling 2FA requires the current password and a current TOTP code. Admin login with 2FA enabled returns a five-minute challenge token; it is stored hashed, is single-use, and does not issue either an access token or refresh cookie until the code is verified. One recovery code is consumed atomically on use. Verification endpoints are rate limited. After successful verification, users may trust the current browser for 30 days; its random token is stored only as a hash and sent in an httpOnly, admin-auth-path cookie. A trusted token rotates on use and is revoked when the password changes, recovery codes are regenerated, or 2FA is disabled.


The login UI keeps the challenge token in memory. It is not a session credential and cannot access protected APIs. Admin 2FA is opt-in per account until the owner selects required roles in `/settings/security`; a role policy cannot be saved while an active user in one of those roles has not enrolled. Public customer registration defaults on in `local`, `testing`, and `uat`, and off in other environments; `STORE_PUBLIC_REGISTRATION_ENABLED` or the saved owner setting overrides that default. Session lifetime and per-minute login attempt limits are configurable in the same security settings page.

When a protected direct URL is opened without a session, admin login carries that same-origin path, query, and hash as `returnTo`. Session expiry also preserves the current route. Login and password-recovery routes are rejected as return destinations to prevent redirect loops.

Admin account preference `admin_session_security.idle_timeout_minutes` supports 15, 30, 60, 120, or 0 (disabled). The browser displays a one-minute warning before the configured idle timeout and logs out through the normal admin session revocation endpoint when the countdown expires. User activity is synchronized across tabs with `BroadcastChannel`; no authentication token is persisted for this feature.




## Customer account deletion

`DELETE /api/v1/account` requires the current password and is limited to customer accounts without orders in active fulfillment. It soft-deletes the user and revokes/removes access and refresh sessions, so sign-in is no longer possible. The soft-deleted database row currently retains profile fields (including email, name, phone, and password hash) and role links; no automatic purge or anonymization job is configured. The Storefront privacy notice and production retention period require owner approval before release.

## Storefront passkeys

Customers can register up to ten discoverable WebAuthn credentials from account settings after signing in. Registration and login require user verification and use one-time challenges that expire after five minutes. Customers can remove their own credentials; deleting an account also removes its passkeys. If a device is lost, the customer can use password login or the existing email password-reset flow, then remove the lost credential. Passkeys are an additional sign-in method and do not disable password recovery.
