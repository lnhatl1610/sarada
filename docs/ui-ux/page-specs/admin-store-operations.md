# Admin Store Operations

Shipment editor controls and feedback follow the selected admin locale.

- Table row actions use the accessible shared `⋯` menu for secondary operations. Destructive actions appear last and use the destructive style; high-frequency state controls remain visible in their own column.

This spec covers the admin navigation areas outside dashboard, products, orders, and inventory. Each area is permission-gated, uses server-side pagination and allowlisted sorting for lists, and provides loading, empty, error/retry, and no-permission states.

- Operations screens localize table headings, filters, movement and payment labels, shipment labels, payload actions, and empty/error feedback in Vietnamese and English. Dates, numbers, and VND values follow the active locale.
- Customer management localizes list filters and status tabs, profile details and summaries, address/order/review/wishlist/cart sections, internal notes, edit controls, and API feedback in Vietnamese and English.
- Campaign and banner management localizes coupon types, banner positions, filters, sortable banner controls, loading/empty states, and coupon rule preview labels in Vietnamese and English. Category image, banner, and collection-cover forms require descriptive alt text and send it through the admin and public APIs.

## Categories, brands, and attributes

- Category/brand lists show name, slug, active/published state, product count, sort order, and row actions in the shared `⋯` menu. Category drag handles reorder siblings; the visible drop target on each category nests a dragged category under it, and the root drop area promotes it to a top-level category. The API rejects cycles and invalid parents transactionally. Reordering is disabled while filtered or when the list exceeds its 100-item page.
- Category and catalog-reference forms support create/edit and inline validation; the reference name field is marked required. Category forms also support slug validation, active state, and parent selection, which rejects self/descendant cycles.
- Attribute management supports size/color values used to build product variants. Prevent removal of values still referenced by active variants; explain the conflict and provide a safe archive action.
- Destructive actions require confirmation. Changes refresh related product filters and forms.

## Inventory operations

- Inventory movements are read-only and can be filtered by SKU/product, movement type, staff member, and date range, sorted by displayed movement fields, paged with the shared account page-size preference, and exported as CSV using the active criteria. URLs restore filters, sort, and page on direct navigation and browser Back/Forward.
- Opening the movement screen through in-app navigation reads the current URL when the screen mounts, so a shared filtered link is not replaced by search parameters captured during initial application startup.

## Customers and access control

- Customer editing marks name, email, and status as required; a private internal note must contain 3–2,000 characters and its label shows the required marker.
- Customer list supports quick search and active/blocked tabs with server counts. Counts respect search, registration dates, order-count and delivered-spending ranges, last-purchase dates, province, gender, and email verification while ignoring selected status. These filters are grouped in the advanced-filter Sheet with Apply/Reset, remain URL-backed, and apply to CSV export. Spending totals include delivered and completed orders net of recorded refunds. Never expose password hashes or authentication secrets.
- Customer list and detail show an avatar with an initial fallback; relative storage paths are resolved against the API origin. Customer detail shows profile and default-first addresses, order history, reviews, wishlist products, and cart items with snapshot prices, plus cart count/value summaries. Staff with `users.manage` can append private internal notes; notes show author/time and are excluded from storefront APIs.
- Operational tables sort on the server by their displayed fields: order/payment amount/status/time; shipment status/carrier/tracking/timestamps; movement SKU/type/quantity/time; customer name/order count/spend; cart item count/value; wishlist count/product; and staff name/email/role/status. Sorting uses a section-specific allowlist and stable ID tie-breaker.
- Abandoned carts keep search in the quick bar; inactivity threshold (default 3 hours), total-value range, registered-customer/guest type, and date range are grouped in the advanced-filter Sheet. Rows identify guests explicitly and show customer contact, item count, cart value, and last update; the contact action uses email or phone when available. A read-only drawer shows all cart lines, saved unit prices, quantities, current stock, expiration, and totals without exposing guest session tokens. CSV export uses the active search and filters.
- Wishlist management switches between product and customer groupings. Product view shows category, favorite count, current inventory, and latest favorite date; category and date filters are grouped in the advanced-filter Sheet. Customer view shows customer name/email, favorite count, latest favorite date, and date filtering in the same Sheet. Search, sorting, pagination, URL state, and CSV export follow the active view and filters.
- Role/permission screens show role name, assigned permissions grouped by capability, member count, and audit history. Warn before removing a permission that affects active staff; the API enforces every action.
- The staff list displays avatar or initials, name, email, phone, role, status, and account dates. Staff create/edit fields use shared form controls with inline validation; phone numbers use the Vietnamese `0xxxxxxxxx` or `+84xxxxxxxxx` format and remain unique. The temporary-password generator is a separate action from the password label, uses cryptographic randomness, and marks the generated value as dirty. Passwords must include letters and numbers. The API prevents self-lockout and serializes admin demotion, lock, and deletion checks so concurrent requests cannot remove the last active admin.
- Staff views include all, active, pending approval, blocked, and invited tabs; quick search covers name/email/phone, while role and last-login date range are grouped in the advanced-filter Sheet with Apply/Reset. Pending approvals and invitations use the shared server-paginated, sortable DataTable and search their own relevant fields. Row actions support edit, lock/unlock, emailed password reset, revoking every access/refresh session, and opening the staff member's activity log. Operators cannot lock themselves or revoke their own sessions; only the store owner can manage admin accounts.
- The role screen groups permission rows by module, shows assigned staff counts and role descriptions, protects the store-owner role, and provides select-all controls by role and permission. Saving a change that removes permissions from a role with assigned staff requires confirmation; API authorization remains authoritative.
- The staff page and account menu can start a session as an active non-admin employee. A sticky banner names both the acting admin and employee, shows the 30-minute expiry, and offers an exit action. While active, sensitive password, email, two-factor, session, and API-token controls are blocked; API writes are audited with both identities.
- Activity-log search covers the actor, API path, and recorded object values; staff member, module, action (including login/logout and data exports), IP address, and date range are grouped in the advanced-filter Sheet with Apply/Reset. The module filter covers all admin route modules. The detail drawer compares redacted `before` and `after` values by field, and CSV export streams all rows matching the current filters. Successful CSV/report exports are recorded with their active query filters, and the action filter can select `Xuất dữ liệu`. Successful admin login (including completed two-factor login) and logout are recorded without credential or token data. Account activity also records profile/avatar, email-change request and confirmation, password, session, preference, and two-factor changes; password values, 2FA secrets/codes, and session tokens are never stored. Audit snapshots resolve the affected record for staff invitations and roles, staff session revocations and staff soft-deletion session revocation, customers and customer notes, inventory variants, manual and CSV inventory receipts, multi-SKU adjustment vouchers, payments/refunds, shipments, product variants and full image galleries, catalog options including color/size aliases, and the existing content/order resources. Product creation, duplication, and variant creation include new variant, inventory, initial-stock movement, and image records. Product update/delete requests also compare associated variants, images, inventory, latest stock movements, and product-to-tag/collection links, recording only rows and fields that changed. Order status changes include related inventory movements, stock/reservation changes, coupon usage changes, payments, and order history; manual order creation records item, inventory reservation/movement, payment, and coupon changes. Settings writes compare only the submitted key-value settings; secret-like values, including bank account numbers, are hidden while changed fields remain detectable. Core bulk order/product/review actions, inventory threshold updates, catalog/banner/image reordering, collection product ordering, and tag merges record changed fields grouped by record ID. Shipment/payment operations include related payment, shipment, and history changes. Role assignments, permission matrices, product-to-tag/collection links, and collection membership changes are included in the same before/after snapshots; deleting a collection also records its cascaded product memberships. Creates include their new staff/product links. Successful multipart admin uploads outside inventory CSV import record the created file name, MIME type, byte size, SHA-256 digest, and stored URL path in before/after detail rows; file bytes and signed URL query values are never copied into the audit log. Inventory CSV imports keep their bounded inventory-row snapshots. Nested values are capped and successful API result summaries remain available for writes whose affected records are not captured.

- Sensitive resource fields are compared before redaction so audit entries still expose a `changed_fields` marker while both before/after secret values remain masked. The legacy admin password-change endpoint uses the same account audit, including safe session snapshots.
- Accepting a staff invitation writes a personal activity entry in the same transaction as account creation, role assignment, and invitation acceptance. Its path omits the invitation token and its changes never include the password.

## Payments and shipments

- Shipment filters include carrier name, status, and sent-date range. Carrier filtering is applied on the server and carries through URL state and CSV export. Quick status tabs show server counts for all, waiting pickup, in transit, delivered, and failed/returned rows; counts use the current search, carrier, and date filters while ignoring the selected status.

- The payment list keeps order code/transaction reference search and quick status tabs in the list header. Method, date range, and amount range use the advanced-filter Sheet. Tabs show counts with the other active filters applied. It shows successful, pending, failed, and refunded totals using the same active filters as the table, and exports the filtered rows to CSV.
- E2.1 order address editing is available only before delivery and uses dependent province then commune/ward selectors from the bundled official administrative catalog. It retains a historic district field when present. E2.2 manual orders use the same selectors and send current official province/commune codes with display names; province codes continue to drive configured shipping rates.
- Payment payload details open in a side Sheet, format valid JSON for inspection, and redact credentials, tokens, card data, and signatures before returning them to the admin UI.
- Payment details show the transaction reference, linked order, customer contact, method, amount, payment/order states, timestamp, refund history, remaining refundable amount, and sanitized payload. Pending COD payments can be marked collected with an audit note. Refunds accept a positive integer VND amount up to the remaining captured amount and require a reason; rows are append-only and payment/order statuses become fully refunded only when the captured amount is fully returned.
- Shipment list has quick tabs for waiting pickup, in transit, delivered, and failed/returned rows; search covers order code, tracking code, recipient name, and phone, while the date range uses the advanced-filter Sheet and remains URL-shareable. Tabs display server counts based on the other active filters.
- Shipment rows show recipient, phone, and delivery address, link to the order, support editing carrier/tracking/status, and print an escaped shipping label with the available order snapshot. CSV export includes recipient and destination fields.

## Customer reports

- New account counts and the daily timeline count users assigned the `customer` role whose account was created within the selected dates.
- First-time and returning buyer segments use paid orders in the selected period. A buyer is returning when the same account, normalized email, or normalized phone has a paid order before the period starts; guest and registered orders can match through their shared contact. The order count shown is limited to the selected period.
- Customer aggregation uses account ID first, then normalized email, then normalized phone, and finally individual order ID. Display names are not customer identifiers. API table keys use app-keyed HMAC values and do not expose contact identifiers.
- Top customer spending uses the same identity rules and includes only paid orders in the selected period. CSV export contains the registration timeline, buyer segment, province totals, and top spending rows.
- Revenue, payment-method and coupon totals, customer spending, and product/category revenue subtract recorded refund amounts. Product refund values are distributed across order items in proportion to their line totals.

## Reports

- All report pages share a URL-backed date range and render chart summaries with the corresponding accessible data table. CSV export uses the active date range and section filters; the print action opens the browser's print dialog so staff can save the filtered report as PDF.
- Revenue reports group fulfilled, paid orders by day, ISO week, or month and filter payment method. Summary cards compare revenue, order count, discounts, and shipping fees against the preceding period of equal length. Tables cover the time series, payment method, category, brand, and coupon use.
- Order reports filter by status and shipping province, show counts by status and province, cancellation/return rate, and average minutes from confirmation to shipment.
- Product reports filter by category and brand; they show best sellers, revenue by category and brand, products with no fulfilled sales in the selected period, and current lifetime view/sold counters.
- Customer reports filter new versus returning purchasers and shipping province. Account creation counts are distinct from purchase cohorts; purchase cohorts and top spending follow the identity matching rules above.
- Inventory is a current snapshot even when a date range is selected. Category, brand, and maximum available-unit filters apply to inventory lists. The report includes retail-value estimate, stock status, low-stock attention rows, variants with stock but no fulfilled sale in the period, and an estimated sell-through rate. Sell-through is units sold in the period divided by period units sold plus current available units; it is an operational estimate, not an accounting turnover ratio.
- Coupon reports filter by code and date range and include usage count, discounts, and fulfilled revenue. Inventory attention and stagnant-stock lists are capped at 100 rows and link back to the relevant management screens where applicable.
- `/reports/schedules` creates owner-scoped daily, weekly, or monthly email schedules in an IANA timezone, with CSV or PDF output and directly configured report parameters. Creating or managing schedules requires `reports.view` and `reports.schedule`; recipients must be active staff with `reports.view`. Due jobs are queued by Laravel's minute scheduler and generated files are recorded as `scheduled_report` exports for seven-day private storage.
- `/downloads` lists the authenticated admin's personal-data ZIPs and scheduled report files, shows queue progress and expiry, downloads through the authenticated API, and supports deletion. Admins with `exports.view_all` can see every listed export; failed scheduled reports can be queued again.

## Coupons and reviews

- Coupon list/form covers running, upcoming, expired/exhausted, and disabled tabs with server counts; counts respect search, type, and effective-date filters while ignoring the selected status. It also covers minimum order value; global/per-user limits; percent cap; and a permission-gated active switch. Staff can duplicate a coupon with a newly generated code, generate a code in the form, and inspect paginated orders that used a coupon plus total discount. The form validates code format, discount values, limits, and date order inline, and previews the rule before saving. `/coupons/create` and `/coupons/:id/edit` open the corresponding form and load the selected coupon; edit reads require `coupons.view`, while edits require `coupons.manage`.
- Banner management filters by display position and active state, searches by title, groups rows by position, and supports order drag-and-drop when the complete unfiltered position list is loaded. It supports URL-backed filters, the shared 10/20/50/100 page-size preference, and an explicit clear-filters state when no rows match. The editor previews the image in desktop and mobile frames and includes title, image, link, position, order, schedule, and active state.
  - Banner destinations accept only root-relative internal paths or absolute HTTP(S) URLs. The Admin form validates this before submission and the API enforces it; Storefront renders any legacy unsupported destination as non-clickable text.
  - Banner video sources accept only absolute HTTP(S) URLs. Unsafe legacy values are ignored on Storefront, which retains the banner image as the visual fallback.
  - Banner records support optional editorial copy up to 500 characters. Admin validates and saves this field; the public banner API returns it for Storefront hero/campaign captions.
- Content pages filter by published/draft state and title or slug. Their title, publish state, and update-time columns sort on the server with URL-backed state. The editor uses the shared rich-text controls, sanitizes unsaved markup through the formatting-tag allowlist before rendering its preview, stores server-sanitized HTML, edits SEO title/description, and offers editable starter templates for returns, shipping, privacy, terms, about, and contact pages. These templates create new pages; existing published policy pages continue to use the Storefront-linked `privacy` and `terms` slugs and should be edited from their existing rows.
- Review moderation uses pending, approved, and hidden tabs with server counts; counts respect search, rating, image, verified-purchase, fit, and date filters while ignoring the selected status. Search matches review text, customer, and product; filters cover 1–5 stars, image presence, verified purchase, fit, and submitted date range, with values reflected in the URL. Rows show product, customer, rating, truncated title/content, image count, purchase verification, status, date, and row actions. Visible review columns sort on the server; sort state is URL-backed, and sortable fields are validated by the API. Bulk review moderation uses the shared table selection controls, including select-all-on-page and Shift-click ranges, and enforces the API's 100-row limit in the UI.
- Review details open in a right-side drawer with the full review, zoomable attached images, moderation reason, and a link to its related order. Staff with `reviews.moderate` can approve, hide with a required 3–1,000 character reason, or delete; bulk approve and hide apply to up to 100 selected reviews. Local and API validation for a hide reason appears inline beside the field. Review status changes and deletion recalculate product rating count/average; those affected product fields are included in the same before/after activity snapshot. All public ratings aggregate approved reviews only.
- Review moderation tabs, filters, bulk actions, table labels, accessible names, empty/error feedback, and count summaries use the selected admin locale.

## Content and settings

- Banner management supports its existing schedule, image/alt text, ordering, and destination fields. Page management uses the existing `pages` schema (`title`, unique `slug`, sanitized rich-text `content`, SEO fields, and `is_published`) with create/edit/delete, search, pagination, preview, and publish/draft controls. The editor and public page render sanitized rich text with matching content typography and spacing; page schedules and page-specific images remain outside the current schema.
- Banner editors can upload JPG, PNG, or WebP images up to 2 MB through the shared Admin media endpoint; the returned public URL fills the image field and feeds desktop/mobile previews. They can upload MP4 videos up to 5 MB into the same public media library; the returned URL fills the video field and updates its preview. The endpoint accepts `content.manage` alongside product create/update permissions.
- Banner list thumbnails and desktop/mobile image previews resolve relative media paths against the configured API origin. The editor keeps the API-provided image value unchanged when saving.
- Category, brand, and collection thumbnails and upload previews, store logo/favicon/Open Graph previews, and review-image/zoom previews also resolve relative media paths against the configured API origin. Form values and API payloads keep the original media paths unchanged.
- The product-create wizard resolves entered relative image URLs against the API origin for both the sortable gallery and primary-image preview, while keeping selected local-file blob previews intact.
- Public pages include about, shipping/returns, contact, privacy, and terms. Settings expose public store name/contact/shipping thresholds and require confirmation for changes affecting checkout.
- Store settings section titles, fields, instructions, client validation, loading/retry states, and save/test-email feedback use the selected admin locale. Saved email templates and the storefront maintenance message remain editable store content.
- Preview and published state must be distinguishable. Do not show dead links or success messages when an API operation failed.
- Shipping settings include editable shipping methods and a province-rate table with code, name, integer VND fee, optional free-shipping threshold, active state, search, sort, and pagination. Method name/fee and province code/name/fee are marked required and validated as non-negative integer VND; free-shipping threshold remains optional. Inactive or missing province rates fall back to the global fee and free-shipping threshold; the same rule is used by storefront and manual-order calculations.
- Shipping method and province-rate pages localize filters, table headings, statuses, accessible row actions, validation, API errors, confirmations, and save feedback with the selected admin language. VND values use the shared locale-aware formatter; province and method names remain user data.

## Acceptance criteria

- [x] Each navigation item resolves through a typed page registry and direct-path map to a dedicated screen, or to an explicit forbidden/not-found state; no navigation entry falls through to the dashboard.
- [x] Operational lists use server search/filter/sort/pagination and explicit loading, empty, error, and retry states; bounded report/detail tables render their complete aggregate or snapshot payload without list pagination.
- [x] Permission checks hide controls in the UI and protected API route groups enforce the corresponding permission middleware.
- [x] Mutations show validation, confirmations for destructive actions, success/error feedback, and audit context where required; the source audit covers registered admin mutation routes and admin-side pivot writes.
- [x] Published content has a preview using the storefront's content title and body typography, spacing, and list/blockquote styles; both API resources sanitize content with the same allowlist.
- [x] Review rating, image, purchase verification, fit, and date filters use the draft advanced-filter Sheet; Back/Forward restores URL-backed filters and page.
- [x] Customer, activity-log, staff, operation, and review lists show removable chips for applied criteria and clear all relevant filters together.
- [x] Coupon, banner, catalog-reference, content-page, personal-activity, shipping-method, and province-rate filters show removable chips and preserve URL-backed filter state.
- [x] Sidebar destinations match the planning paths, authorized empty groups stay hidden, collapsed groups expose their destinations in a popover, and alert badges cover pending orders, failed deliveries, low stock, pending reviews, and pending staff approvals.
- [x] Search text stays responsive in the input while list and lookup requests wait for a shared 300 ms debounce; URL search state updates immediately.
- [x] Payment collection and refund dialogs map server validation errors to the amount and note/reason fields; COD collection from order detail maps the `note` validation response inline.
- [x] Product, order, inventory, and review list headers sort using validated server fields and preserve sort direction in URL state.
