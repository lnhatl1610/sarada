# Customer Account

## Authentication

- Login and registration use labeled fields, inline validation, pending/disabled submit state, and actionable server errors. Never place access or refresh tokens in localStorage.
- Storefront login offers an unchecked `Ghi nhớ tôi` choice. When selected, the httpOnly refresh cookie persists for the configured session lifetime; otherwise it is a browser-session cookie, including after silent refresh. Legacy clients that omit the option retain persistent-cookie behavior.
- Storefront registration requires agreement to the published terms and offers a separate, optional marketing-email checkbox that defaults off.
- Login, registration, forgot-password, and reset-password use React Hook Form with Zod validation. Registration/reset follow the password policy returned by the public Storefront configuration; field errors are programmatically associated with their controls.
- Forgot-password and reset-password screens explain email delivery and token expiry without revealing whether an email is registered. Support password change for an authenticated customer.
- Authentication redirects accept only safe relative `returnTo` values. After login, restore the intended page and merge the guest cart.
- If an authenticated Storefront request gets 401 and the shared refresh request is rejected with 401/419, the customer is sent to login with an expiry notice and a “Đăng nhập lại” action. Login preserves the current same-origin route, query, and hash; a network or server failure during refresh does not claim that the session expired.

## Account area

- `/account/vouchers` lists server-derived public coupon availability and the customer's usage history, with status filters, eligibility terms, expiry dates, empty/loading/error states, and pagination. Each code has a copy action with announced success and a manual-copy fallback message if clipboard access is unavailable. Customers can enter a new code here; the code is sent to the cart, where the current cart and province quote determine eligibility before checkout.
- `/account/notifications` lists the signed-in customer's order-created, shipment, price-drop, and newsletter welcome-promotion updates, shows unread state and timestamps, supports marking one or all as read, and links to the matching order, product, or offer. The API scopes every read and write to the current customer; guests receive order and consented newsletter email only.
- `/account/notifications/preferences` stores per-event choices for orders, promotions, and product price drops. Enabling promotion email explicitly subscribes the account email to newsletter marketing; turning it off withdraws that consent. Email and in-account delivery are selectable when available; browser push requires a registered device and configured VAPID keys; SMS requires a phone number and configured Twilio sender. Zalo ZNS remains disabled until the store configures that provider.
- Storefront account pages share one responsive account center. `/account` is an overview with the latest API-backed order, saved delivery address, and shortcuts. The customer identity and logout action stay in the page header; overview, profile/security, orders, addresses, and wishlist remain reachable from persistent sidebar navigation that becomes a horizontally scrollable row on small screens. The active section is announced with `aria-current="page"`.
- Account settings keep their profile, email, password, active sessions, and account deactivation controls in a second-level tab bar. Unsaved changes still block navigation with an accessible confirmation.
- The Passkey tab lists only the signed-in customer's credential names and usage dates, supports browser-native WebAuthn registration and confirmed removal, and explains that password reset remains the recovery path if a device is lost. Passkey login is available on supported browsers; password login remains available as a fallback.
- Customer profiles may store height, weight, bust, waist, and hip measurements. These optional values are visible only through that customer's account profile; height and weight prefill the PDP size calculator, where the customer can edit them for the current product.
- Body measurements are included in the authenticated personal-data export and cleared when a customer deletes their account.
- Customer account settings let the signed-in owner queue a personal-data ZIP export, poll its status, and download the signed file within seven days; exports and downloads are limited to the current account.
- Empty wishlist, saved-address, and order-history states include decorative, screen-reader-hidden illustrations; the empty order history links directly to the catalog.
- Guests can open `/wishlist`, save and remove public products in guarded local browser storage, view current catalog prices/variants, and add selections to cart. After sign-in, guest product IDs are merged into the customer's default list; failed merges keep their local references. The account wishlist stays behind authentication and exposes price/restock alerts and share links.
- Wishlist cards let customers enable/disable a product-level email price alert and request a restock email for each sold-out variant. Price alerts are customer-owned and reset their effective-price baseline when re-enabled; restock alerts follow the selected variant.
- Wishlist lets customers choose an in-stock color/size for each saved product and add the eligible selections sequentially to the cart. Products without a selected in-stock variant are skipped or must be selected before bulk add; partial failures report added/failed counts and leave the saved list intact.
- The order list has URL-backed status tabs, search by order code or purchased product, inclusive date filters, and server pagination; the API only returns orders owned by the signed-in customer.
- Order details provide “Mua lại” by sending each saved variant and quantity through the current cart API. The server checks current availability and pricing; unavailable lines are reported while successful lines remain in the cart.
- Order details show each customer cancellation/return request with its current decision and staff response, plus the total VND refunded and each refund amount/time. Guest order tracking shows refund totals and timestamps too. Refund reasons and staff-only metadata are not exposed.

- Storefront profile and session reads are cached per customer with TanStack Query; loading failures show a retry action. Profile, email, avatar, and session changes update or invalidate that customer-scoped cache, which is cleared on logout or account deletion.

- Profile settings at `/account/settings` edit a required 2–100 character name, Vietnamese phone, gender, birthday, and avatar. Email, role, account status, creation time, and last login are read-only. The admin profile form has explicit Save and Cancel actions; Cancel confirms before discarding edits. Admin avatar uploads preview the selected image, allow keyboard-adjustable square cropping, report unreadable image files, and upload a 512 × 512 result. Removing an existing avatar requires confirmation and keeps API errors in that confirmation dialog. Email changes require the current password; the old address remains active until a single-use link sent to the new address is confirmed. Password changes require a different password, show a four-level strength meter and checklist (minimum length, letter, number, recommended special character, and difference from current password), and send an email security notice. The admin option to log out other devices is checked by default; the active session remains valid and trusted-device records are always revoked. Customers can inspect/revoke sessions and request account soft deletion after confirming their password. Session entries show parsed browser/version, operating system, device type, IP, login time, last activity, and identify the current session. The admin account page at `/settings/account` provides profile, email/password, and session controls without customer address or account deletion actions.
- Customer avatar uploads validate JPG/PNG/WebP and the 2 MB limit before opening a keyboard-operable square crop dialog with rotate, zoom, horizontal/vertical positioning, an accessible preview, and a 512 × 512 output. Unreadable images and API upload errors remain visible; cancel closes the dialog and restores focus to the upload control.
- Storefront account settings warn before SPA navigation or closing the tab when profile, email, password, or deletion form values have unsaved changes; successful saves reset only the submitted form. Customer session rows show parsed browser/version, OS, device type, IP when supplied, last activity, and current-session status.
- Revoking one session or all other sessions opens an in-app modal that identifies the selected device or explains which sessions will be ended. The current device remains signed in. While the request is pending, both actions are disabled; Escape/cancel returns focus to the trigger, and success returns focus to the session heading after the revoked row is removed.
- Account profile, email, password, and deletion field errors are linked to their inputs with `aria-invalid` and `aria-describedby`; recoverable API validation failures preserve form values.
- Logging out from the admin account menu requires confirmation; confirming calls the existing logout endpoint to revoke the current session before returning to login.
- The account menu's Security submenu links directly to password change, login email, and 2FA sections on the security page.
- The admin account menu links to the storefront root in a new browser tab, alongside account and help actions.
- Disabling two-factor authentication and replacing recovery codes require an explicit confirmation; replacing codes warns that the previous set becomes invalid. Both actions still require the current password and authenticator code.
- Password fields in admin forms provide an accessible show/hide control while retaining their autocomplete and validation behavior.
- The admin account area shares navigation for profile, security, sessions, notifications, activity, appearance, privacy, and permission-gated API tokens. It stays beside page content on desktop and becomes a horizontally scrollable navigation row on narrow screens. Links expose the active page to assistive technology and use the SPA route guard to confirm before leaving unsaved edits.
- The admin session page uses the shared table with browser/version, operating system/device, IP, login/last-activity times, and current-session status. Row and bulk logout actions require confirmation. When an active session uses an IP different from the current device, show a security notice with guidance to revoke unrecognized sessions.
- The admin `/account/sessions` list is server-paginated at the account's 10/20/50/100 page-size preference, and its page is URL-backed. The API retains its unpaginated response for callers that omit `page` and `per_page`.
- The admin session list supports URL-backed server sorting by device, IP, login time, and last activity; the current session remains first for security context.
- The admin personal activity list supports URL-backed server sorting by time, module, action, path, and IP.
- The admin `/account/notifications` page combines per-event in-app/email preferences with persisted personal history, unread count, single-item read state, and mark-all-read. The topbar bell shows the latest saved items and links to the full history; event records are scoped to the signed-in admin and current permissions. Admins with `reports.view` who enable the weekly-report channel receive a summary of the previous Monday–Sunday period on Monday at 08:00 in the application timezone; the notice links to that period's revenue report.
- The topbar bell reports failures when marking an individual notification read or marking all notifications read; failed individual actions leave the user on the alert and can be retried.
- The admin `/account/activity` page is scoped to the signed-in account, supports URL-backed module/action/date/page-size filters, uses the shared paginated table, and opens a detail sheet for each audit entry. Profile/avatar, email, password, session, preference, and two-factor writes record changed fields; the signed email-change confirmation records the safe email before/after pair. Passwords, 2FA secrets/codes, and session tokens are never stored in these audit entries. The sheet compares before/after when the audit record contains snapshots and otherwise labels the recorded request values explicitly.
- Address book lists default and saved addresses with add/edit/delete and default selection. New addresses use the current two-level province/commune catalog; older district-based addresses remain readable and editable during migration (ADR-0013).
- Deleting a saved address opens an in-app modal confirmation with the selected recipient/address, cancel action, pending state, and visible API error. Escape or cancel returns focus to the triggering delete button; successful deletion moves focus to the address-book heading because the deleted row and trigger no longer exist. Do not use a browser-native `window.confirm` for this flow.
- Deleting a customer account requires a valid current password before opening an in-app confirmation dialog. The dialog explains that the account is deactivated and sessions are signed out, disables both actions while the request is pending, supports Escape/cancel with focus returned to the trigger, exposes recoverable API failures accessibly, and returns focus to the password field when the server rejects the password. Do not use a browser-native confirmation for this flow.
- Removing an existing avatar opens an in-app confirmation dialog. API errors remain visible inside it; cancel/Escape returns focus to the removal trigger, and successful removal moves focus to the account-settings heading because the trigger becomes disabled.
- Attempting SPA navigation with unsaved account form values opens an in-app confirmation dialog. Staying resets the blocked navigation and returns focus to its trigger; proceeding discards the values and continues. Reload/tab-close warning uses the browser `beforeunload` prompt.
- Address book maps API validation errors for recipient, phone, street, province, and ward to their fields with accessible descriptions; failed saves preserve the entered address. Changing province clears only the ward selection and preserves the other fields already entered.
- Order list shows code, date, total, payment and fulfillment states, with links to details/tracking. Detail shows order date, payment method/status, item/address/total snapshots, carrier/tracking codes when available, and status timeline; customers can print/save a PDF order summary and open a support request with the order code prefilled. Customers may request cancellation before shipment or return within seven days of successful delivery, with staff review and a reason-confirmation dialog. The detail shows the return deadline and hides/disables the request action after expiry; the API enforces the same deadline using `delivered_at`.
- Guest order tracking asks for the order code and the matching phone number or email used at checkout. A missing order and a mismatched contact use the same not-found response.
- Wishlist supports add/remove from cards and detail pages, move-to-cart when available, and empty/unavailable states. Customer reviews are linked to eligible purchased items and show moderation status privately. Authenticated order details expose only each purchased item's review status; guest tracking never includes it, and staff moderation notes remain private. Already-reviewed items cannot be selected again, and switching between order details clears the review draft.
- Review submission validates the purchased item, a 1–5 rating, 160-character title, and 5000-character content; title or content is required. Field errors are linked accessibly, API failures preserve the draft, and a successful submission resets it while the moderation status updates privately.
- First-time customers see useful empty states with a direct action to shop, add an address, or browse products.

## Admin account security

- `/account/security` supports password and verified-email changes, plus optional TOTP enrollment using a QR code or manual key.
- Password change defaults to revoking other sessions while preserving the active session; trusted-device records are revoked on every password change. The page shows a four-level strength meter and checklist, and queues a security email after success.
- TOTP is active only after a six-digit authenticator code confirms enrollment. Eight recovery codes are displayed once, can be copied or downloaded, and each code can be used once.
- Replacing recovery codes and disabling TOTP require the current password and a current authenticator code.
- When admin TOTP is active, password login returns a five-minute, single-use challenge. The SPA completes it with a TOTP or recovery code before it receives an access token or refresh cookie.
- Six-digit TOTP entry uses six labeled cells with automatic focus advance, arrow-key navigation, paste, and one-time-code autofill. Recovery codes remain a single text field.
- `/settings/account/privacy` lets admins queue an owner-scoped personal data ZIP, review progress and download it from a signed seven-day URL, clear local and session browser storage plus query cache without logging out, and read current data retention periods.
- Admins with `api_tokens.manage` manage personal API tokens at `/settings/account/tokens`: select a name, explicit permission subset, and 7/30/90-day expiry; enter ten-minute session-scoped sudo mode (including TOTP when enabled); show the plaintext once; and list scopes, created/last-used times, last-use IP, expiry, and revoke action. The page caps each admin at 10 tokens and hides the navigation item from admins without the permission. Non-expiring token creation appears only when the owner enables it in Security settings.

## Acceptance criteria

- [x] Password recovery, profile/password editing, address CRUD, order details, wishlist, and eligible review entry are reachable from account navigation.
- [x] Wishlist lets customers choose an available color/size variant before adding it to the cart; sold-out choices stay disabled and cart synchronization failures can be retried.
- [x] Wishlist exposes price-alert status and per-sold-out-variant restock signup with loading and success/error feedback.
- [x] Wishlist can add all selected in-stock variants to the cart sequentially, reports partial failures, and keeps the saved list intact.
- [x] Wishlist supports customer-owned lists with create, rename, delete, per-list product membership, and revocable read-only share links. Deleting the active default list creates or promotes its replacement; shared links show only currently published products.
- [x] Profile avatar, email verification, session revocation, and customer account soft deletion are available from account settings.
- [x] Customers verify a new/current phone by SMS before changing it or signing in by phone; profile edits cannot bypass verification.
- [x] Redirect target is validated as a safe relative path.
- [x] Cancellation and return requests appear only in API-eligible states and use an accessible reason dialog with an explicit submit action.
- [x] Return requests are available through seven days after `delivered_at`; the deadline is shown in the order detail, expired requests are hidden from the UI and rejected by the API. The Storefront demo-data audit verifies an in-window pending request, an expired order without a pending request, and matching order/shipment delivery timestamps.
- [x] Forms preserve values on recoverable errors and expose accessible field errors.
- [x] The address book saves Nhà/Công ty/Khác labels and independently manages delivery and invoice defaults; changing either default does not replace the other.
- [x] Admins can enroll, confirm, recover, replace recovery codes, and disable optional TOTP authentication; completed login challenges do not issue session credentials before verification.
- [x] Customer and admin session lists expose readable browser, OS, and device labels alongside IP and activity timestamps.
