# Functional Requirements

Priority: Must unless marked Should/Later. Status is Planned until implemented and reviewed.

## Authentication and access
- **FR-AUTH-001** The system must register customers with a unique email and securely hashed password. Must. Verify duplicate email is rejected.
- **FR-AUTH-002** The system must issue short-lived audience-scoped JWT access tokens and rotate opaque refresh tokens stored hashed server-side. Must. Verify old refresh token reuse revokes its token family.
- **FR-AUTH-003** The system must return the authenticated profile and permissions for the correct audience. Must. Verify storefront token cannot access admin routes.
- **FR-AUTH-004** The system must support logout, password change, forgot-password, and reset-password flows. Must. Verify revoked sessions cannot refresh.
- **FR-AUTH-005** Public customer registration must be enabled by default when `APP_ENV` is `local`, `testing`, or `uat`, and disabled by default in other environments; an explicit `STORE_PUBLIC_REGISTRATION_ENABLED` environment value or saved owner setting must override that default. Must. Verify registration status and registration submission use the same effective value in each environment.

## Catalog
- **FR-CAT-001** Staff must create, edit, archive, and publish products with categories, brands, tags, images, and SEO fields. Must.
- **FR-CAT-002** A product may contain size/color variants with unique SKU, price, active state, and inventory. Must.
- **FR-CAT-003** Shoppers must browse/filter/sort/search published products and see only active variants and available stock. Must.
- **FR-CAT-004** Product detail must include images, variant availability, related products, and approved reviews. Must.
- **FR-CAT-005** Shoppers must be able to read answered questions for published products, and authenticated customers must be able to submit product questions. Staff with review moderation permission must answer or hide questions; the Storefront must expose answers only after staff publishes them and must never expose customer contact data. Should. Acceptance: public question pagination contains only answered questions for published products; invalid or unsigned submissions are rejected; Admin mutations require `reviews.moderate`; the answer and status persist, and hidden/pending questions are absent from public results. Source: `storefront-full-spec.md` (P1, product Q&A); spec: `docs/ui-ux/page-specs/product-detail.md`; status: implemented; UAT pending.

## Cart and checkout
- **FR-CART-001** Guests and customers must add, update, and remove cart items. Must.
- **FR-CART-002** On login, a guest cart must merge into the customer cart and cap each quantity at available stock. Must.
- **FR-CHK-001** Checkout preview must recompute item prices, coupon discount, shipping, and total on the server without creating an order. Must.
- **FR-CHK-002** Checkout must place one COD order idempotently when a valid `Idempotency-Key` is supplied. Must.
- **FR-CHK-003** The server must lock and validate inventory, snapshot item/address data, reserve or decrement stock, record coupon use, and clear the cart atomically. Must.
- **FR-CHK-004** A guest must be able to submit valid contact and shipping details without creating an account. Must.
- **FR-CHK-005** Shoppers must be able to request the province shipping-fee fallback and currently active delivery methods that apply to a selected province and optional commune/ward, including staff-configured delivery estimates; the response is informational, and checkout remains authoritative for the final fee. Should. Acceptance: valid destinations return the active province fallback, free-shipping threshold, and only eligible configured methods with integer VND fees and configured ETA text; invalid province/ward pairs return 422; inactive or out-of-area methods are excluded; PDP shows loading, retryable error, and empty/configured states on explicit request.

## Orders and inventory
- **FR-ORD-001** Every order status transition must be validated and recorded in status history. Must.
- **FR-ORD-002** Customers may immediately cancel pending orders or submit cancellation requests for pending, confirmed, or processing orders; staff may cancel only before shipping. Must.
- **FR-ORD-003** Customers must view their orders and track guest orders with code plus phone/email. Must.
- **FR-ORD-004** Authenticated customers must be able to submit one pending cancellation or return request for an owned order in an eligible lifecycle state; staff with order-update permission must review it. Return requests must be submitted no later than seven days after the recorded successful delivery time, and the API must reject requests without a delivery timestamp or beyond that deadline. Cancellation approval must use the order state machine, while return approval must not restock or mark the order returned before staff confirms receipt of the goods. Must. Source: `ACCOUNT_MENU_PLAN_FULL.md` and the store owner's confirmed seven-day return-request policy. Acceptance: verify requests just before and exactly at the deadline are accepted, requests after it and orders without `delivered_at` are rejected, and the account UI shows the deadline/expired state. Spec: `docs/ui-ux/page-specs/account.md`; status: API lifecycle UAT verified on 2026-10-27 for ownership, request review, exact deadline, expiry, and inventory restoration; missing-`delivered_at` and Storefront UI state remain open.
- **FR-INV-001** Every inventory adjustment must record actor, reason, reference, and movement. Must.
- **FR-INV-002** Available stock must equal on-hand quantity minus reservations and must never become negative. Must.
- **FR-INV-003** Low-stock variants must be visible in admin dashboard/inventory. Should.

## Promotions, accounts, content
- **FR-CPN-001** Coupons must enforce dates, minimum subtotal, global/per-user usage limits, type, and percent maximum discount. Must.
- **FR-CUS-001** Customers must manage profile and addresses. Must.
- **FR-CUS-002** Customers must manage a product wishlist. Should.
- **FR-REV-001** Only a customer with a delivered/completed order item may submit a review; reviews require staff approval. Should. Acceptance: a review may contain up to five JPG/PNG/WebP photos (2 MB each, 4000×4000 maximum) and one MP4/WebM video (5 MB maximum); pending/rejected review media is not public, and approved media renders with the appropriate accessible image or video controls. Source: `storefront-full-spec.md` (P0, customer review photo/video); spec: `docs/ui-ux/page-specs/product-detail.md`; status: implemented; upload/moderation UAT pending.
- **FR-ADM-001** Staff must be limited by roles/permissions enforced by the API. Must.
- **FR-ADM-002** Authorized staff must manage categories, brands, attributes, products, inventory, orders, coupons, reviews, banners, pages, FAQs, store locations, settings, and users. Must.
- **FR-ADM-003** Administrative mutations must create an audit record. Must.
- **FR-ADM-004** The storefront must display published pages, active banners, and public shop settings. Must.
- **FR-ADM-005** The admin dashboard must summarize revenue, order counts, low stock, and top products. Should.
- **FR-ADM-006** The system must send queued Vietnamese email notifications for account/order events when SMTP is configured. Should.
- **FR-ADM-007** Staff must be able to personalize supported admin display preferences (theme, accent, table density, and motion) and have them persist for their browser. Should.
- **FR-ADM-008** An authenticated admin must be able to open a permission-filtered account menu with cached summary counts, menu search, and locally tracked frequent destinations. Should. Acceptance: the API rejects non-admin audiences, hides counts for unavailable permissions, caches per admin for no more than 60 seconds, and the menu remains usable when counts fail; search supports the documented Vietnamese aliases and recent-use list is scoped to the admin account. Source: `ACCOUNT_MENU_PLAN_FULL.md` sections B3, B4, B6; spec: `specs/21-admin-account-menu/`; status: In progress.
- **FR-ADM-009** An authenticated admin can create and manage private tasks; task assignment to another active staff account requires `tasks.assign`. Acceptance: reads and mutations are scoped to the owner/assignee, task status and completion timestamps stay consistent, linked records and task reminders are supported, reminder notifications follow user preferences, and assignment is rejected without the permission. Private notes and bookmarks were removed by migration `2026_11_04_000002`. Source: `ACCOUNT_MENU_PLAN_FULL.md` sections 2.1 and 2.4; spec: `specs/21-admin-account-menu/`.
- **FR-ADM-010** An admin must be able to review their own login history, account security score, and presence, and revoke all admin sessions. Should. Acceptance: history is owner-scoped and records success, password/2FA failures, and lockouts without credentials; password changes update the security score source; presence writes are admin-audience protected; logout-all revokes admin refresh/access sessions and trusted-device records. Source: `ACCOUNT_MENU_PLAN_FULL.md` sections 0, 1.2, 1.3, 1.8, 9; spec: `specs/21-admin-account-menu/`; status: In progress.
- **FR-CMS-001** Staff with `content.manage` must be able to maintain store locations and publish or unpublish them. The Storefront must list published locations, filter by province, show address/contact/opening hours, provide map and directions, and offer nearby sorting only after the visitor requests location access. Should. Acceptance: public API never returns inactive locations; Admin writes validate coordinates, location text, and status; nearby sorting uses browser geolocation only on explicit action and does not persist the visitor's coordinates. Source: `storefront-full-spec.md` §11 (P1, store system); spec: `specs/22-store-locations/spec.md`; status: implemented; runtime/UAT pending.
- **FR-CMS-002** Shoppers must be able to browse published FAQs grouped by topic and search question/answer text; staff with `content.manage` must be able to maintain and publish FAQ entries. Must. Acceptance: public responses contain active entries only and searching narrows matching grouped results; drafts are absent from public API, sitemap, and structured data; admin mutations are validated, permission-protected, and audited. Source: `storefront-full-spec.md` §11 (P0, FAQ); spec: `specs/23-storefront-faq/spec.md`; status: implemented; runtime/API UAT pending.

## Marketing
- **FR-MKT-001** A visitor who submits a valid email and explicitly consents to newsletter messages must be subscribed immediately; email confirmation is not required. Should. Acceptance: the API stores one normalized email and consent timestamp, returns the same accepted response for new and duplicate submissions, and does not enqueue a confirmation email; missing consent or invalid email returns 422. Source: store owner's confirmed single-step opt-in decision (2026-10-28). Spec: `docs/ui-ux/page-specs/storefront-home.md`; status: implementation present, end-to-end mutation UAT pending.
- **FR-MKT-002** A customer must be able to subscribe to a product price-drop alert from its detail page or wishlist, and to an out-of-stock variant restock alert from either surface. Must. Acceptance: price alerts capture the current effective variant price as a VND integer baseline, notify once by queued email only after a lower effective price is observed, and can be disabled by their owner; account restock subscriptions use the customer's account email and remain scoped to the selected active variant; anonymous PDP restock subscriptions keep their existing email/SMS flow. Source: `storefront-full-spec.md` (P1, customer wishlist and product detail); specs: `docs/ui-ux/page-specs/account.md`, `docs/ui-ux/page-specs/product-detail.md`; status: implementation present, price-transition/email delivery and variant restock UAT pending.
- **FR-MKT-003** The store must queue cart-recovery email reminders one hour and 24 hours after inactivity. Signed-in customers must be active and explicitly subscribed to newsletter email; guests must explicitly consent to reminders for their current non-empty cart and be able to withdraw consent. Each reminder stage must be sent at most once per unchanged cart, and any cart mutation must restart both inactivity windows. Empty, expired, inactive-customer, and non-consented carts must not receive reminders. Must. Acceptance: scheduler claims each due stage atomically, does not queue duplicate stages, resets claims on cart mutation/merge, clears guest consent when the cart empties/expires or checkout succeeds, and links to the canonical cart. Source: `storefront-full-spec.md` (P1, abandoned cart); spec: `specs/03-cart/spec.md`; status: implemented; scheduler/email UAT pending. Zalo delivery is unsupported.
