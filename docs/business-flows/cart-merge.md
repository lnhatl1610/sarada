# Guest Cart Merge

Guest cart is identified by a random `X-Cart-Token`; it is not an auth token. After login, the client sends the guest cart token to merge. Lock both carts in stable ID order, then combine lines by variant and cap each quantity at 20 and current available stock. Remove invalid/inactive, unavailable, and zero-quantity lines from the canonical customer cart; discard the guest cart after a successful merge. Merge is idempotent and returns the canonical cart using the same `CartEnvelope` presenter as `GET /cart`. Add/update/remove mutations lock the owning cart; add/update also lock the variant and inventory before checking availability. Checkout takes the same cart lock before consuming lines so a concurrent cart edit cannot be lost when the order clears the cart.

The Storefront owns the canonical response in TanStack Query, with separate guest and customer cache keys. Successful cart mutations reconcile the server response into that cache; logout removes customer cart data before the guest cart is loaded again.

Guest recovery is separate from newsletter subscription. On a non-empty guest cart, the shopper may submit an email with explicit consent, change it, or withdraw it. The API binds the contact to the existing cart token, exposes it only in that cart's canonical response, and clears it when the cart empties, expires, or checkout succeeds. The scheduled reminder command requires the consented guest contact or, for members, an active account with a matching newsletter subscription; it claims each one-hour and 24-hour stage under a cart lock.
