# Checkout

1. Resolve the optional storefront bearer session; a valid session uses that customer's canonical cart and binds the order to the account, while a request without a bearer uses the guest cart token. Reject supplied invalid, revoked, or admin-audience credentials instead of downgrading to guest scope. Require explicit `terms_accepted: true`, then validate contact, fulfillment selection, cart, and idempotency key. Delivery requires a validated address; pickup requires an active store that can fulfill every cart line from branch stock. A new order must use an enabled method: COD requires `payment_cod_enabled`; manual bank transfer/QR requires the transfer switch and a six-digit bank BIN, bank name, account, and holder. Idempotent replay of an order already created in the caller's scope still returns the original order. The Storefront advertises only configured payment methods.
Invoice requests are optional and separate from the shipping address. When requested, the checkout validates and snapshots the Vietnamese tax code, company name, and invoice address on the order; Admin order detail displays this request. A missing request stores no invoice identity data. Automatic tax-code lookup is not configured, so customers enter and confirm these values themselves.

2. Start DB transaction and lock all requested active variant rows in ascending ID order. Delivery locks online inventory rows by `variant_id`; pickup locks the selected active store and its matching branch inventory rows by `variant_id`. Check stock only in the chosen fulfillment pool.
3. Reject unavailable/inactive variants or insufficient stock with `OUT_OF_STOCK` details.
4. Recompute current price, eligible coupon, shipping rate (zero for pickup), discount, and total server-side.
5. Create order, immutable item/address/payment-instruction snapshots, pickup-location snapshot when selected, pending payment, and initial status history. Bank-transfer orders remain unpaid until staff reconcile the transfer in Admin.
6. Reserve online or branch inventory through `InventoryService` and write movements with the selected store reference when applicable; create coupon usage with the server-calculated discount amount and update usage count. Admin campaign usage history reads this amount. The idempotent order demo seeder reconciles this stored snapshot for an existing demo order on rerun.
7. Clear cart; commit.
8. Queue the Vietnamese order confirmation for the customer and configured new-order alerts after commit.

Shipping fees use an active exact `province_code` rate when configured. That row's fee overrides the global fee, and its `free_shipping_threshold` overrides the global threshold; a null row threshold uses the global value. Missing or inactive province rows use the global fee and threshold. The admin province-rate screen writes these same rows, so storefront quotes, placed orders, and manual orders apply one server-owned rule. Orders retain their shipping fee, method name, and expected-time snapshots after rates or methods change. At checkout, shoppers can also select an active Admin-configured `shipping_methods` option; each option supplies an integer VND fee and optional expected-time text, and can apply nationally, to a province, or to selected wards in that province. The quote filters methods using the current province/ward; the selected method is revalidated and locked during final order pricing, saved on the order, and returned in confirmation and order details. The province-based rate remains the default option. Free-shipping thresholds and free-shipping coupons apply to all listed options.

Variant `price` is charged while its product's optional sale window is active when `compare_at_price` is higher. Outside the window, the comparison price is charged. Products without configured sale dates retain their existing discount behavior. Preview and final order creation evaluate at one timestamp, and each order item stores the exact charged unit price.

The same idempotency key returns the same order only within the original caller scope: authenticated account ID or guest cart token. The stored scope is a SHA-256 digest, not the raw guest token. A different scope receives not found and cannot retrieve the order payload. Legacy orders created before the scope migration have no replay scope and are not returned by the Storefront endpoint. Do not create a duplicate if the client retries after a timeout. Replays return HTTP 200 and do not send another order-created notification. Failed steps roll back all writes.

Non-COD unpaid orders in pending, confirmed, or processing status can be automatically cancelled after the configured number of hours. `0` disables this policy. The scheduler invokes the normal order transition action, which writes history and releases inventory reservations and coupon usage. COD orders are excluded. The local `npm run dev` command starts the scheduler and database queue worker alongside the three app processes.

For bank-transfer checkout, the API returns a scoped payment access token with the placed-order response. The payment page exchanges that token for the order's snapshotted bank details, amount, reference, and expiry; it does not reveal customer or address data. The order confirmation email repeats the destination account, amount, and transfer reference so the customer can recover the instructions later. VietQR is rendered from the bank BIN/account, amount, and order reference. The store must reconcile the actual bank transaction manually before marking the order paid; the QR image does not verify settlement.

## Admin manual order

Staff with `orders.update_status` can create a manual COD order from `/orders/create`. The API accepts customer/contact and address snapshots, selected variant IDs and quantities, an optional active shipping method, and an optional coupon code. It locks active variants and inventory, checks available stock, reads prices from the database, calculates eligible discounts and shipping, writes order/item/payment/status snapshots, reserves stock through `InventoryService`, and records coupon use in one transaction. The client must send an `Idempotency-Key`; repeating the same key returns the existing order. Client-submitted prices and totals are never accepted.
