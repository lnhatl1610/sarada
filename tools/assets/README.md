# Storefront demo asset workflow

`npm run audit:demo-data` at the repository root runs the read-only Storefront API, Admin API, and media coverage audits in one command. It reads the configured local database and media disk without creating or updating records.

`npm run assets:storefront` regenerates photo-based category/collection covers and campaign banners, the campaign video, and the Open Graph image. It runs the renderers in order and stops if any renderer fails. It requires Node.js, Chrome or Edge, and FFmpeg. Set `CHROME_PATH` or `FFMPEG_PATH` when the executables are not at the default locations. The distinct `Trang phục` outfit cover is sourced from `source-photos/category-trang-phuc-v2.png` and rendered as `category-trang-phuc-photo-v2.webp`.

`npm run assets:storefront:verify` runs the full renderer again and compares SHA-256 hashes for all tracked generated outputs and photo sources. It exits unsuccessfully if output differs from the existing generated set, so run it when confirming a renderer change or a clean local setup.

The storefront uses photo-based demo assets instead of geometric graphic placeholders. Product demo photos are managed with `python tools/assets/prepare-ai-demo-product-photos.py --source-dir <generated-images-directory>`; repeat `--only <slug>` to convert a selected set. The command creates one 600×800 WebP for each active generated-v5 product.

`npm run assets:storefront-og` renders the source `storefront/public/og-image.svg` to a 1200×630 JPEG under 150 KiB for Open Graph and Twitter cards. It uses headless Chrome or Edge and FFmpeg; set `CHROME_PATH` or `FFMPEG_PATH` if either executable is not at a default location. The script verifies the image signature, dimensions, and size limit.

The photo renderer uses approved photo sources, Chrome or Edge in headless mode, and FFmpeg with WebP support. It renders 800×1000 category/collection covers, 1600×900 desktop and 720×900 mobile campaign banners, and a short campaign MP4. It verifies image dimensions and size limits (covers under 80 KB, banners under 150 KiB, video under 5 MiB).

`StorefrontDemoSeeder` links these covers into the existing category and collection records. It replaces only null/demo asset URLs, preserving an image or banner that a store operator has replaced with their own upload.

The photo-media renderer uses local source images in `tools/assets/source-photos/` plus existing product demo photos. It does not add visible text overlays to image files. Demo status remains available in image descriptions and asset metadata. Demo assets are local seed data; review a batch before using it as production brand content.

The A3 desktop/mobile layout is approved. The user has authorized photorealistic AI flat-lay garment images with no people or illustrations for local demo/UAT. These images are not verified photos of the store's real stock. Do not present them as actual inventory photos. Replace them with store-provided photographs before production merchandising; operator-uploaded photos take precedence and are preserved by the seeder. Products without an available image render a plain neutral surface.

The Storefront demo seed uses versioned photo-based campaign banners, collection/category covers, and AI-generated item-only flat-lay photos for the seeded product catalog. Every AI image has disclosure in its alt text and a visible Storefront badge. Operator-uploaded product images remain in place. Missing product photos render a neutral CSS surface.

As of 2026-11-06, each demo product retains one medium 600×800 WebP. Sixteen apparel designs use the generated-v5 images; the tote, silk scarf, and mini wallet use their flat-lay images. `StorefrontDemoSeeder` links them only where the current product image is still demo-managed and preserves store-uploaded photos.

Each active demo product keeps one 600×800 WebP at `api/public/demo-media/products/*-photo.webp`. Product image variants, AVIF copies, and superseded versions were removed to reduce duplicate media. API image responses use the retained 600-pixel image directly.

Storefront catalog, product detail, home merchandising, related products, and wishlist pages use the shared `storefront/src/components/shared/ResponsiveImage.tsx`. If an API image is absent or fails to load, it shows a plain neutral surface without substituting a graphic illustration. The component accepts server-provided `srcSet` and `sizes`; no descriptors are fabricated for operator uploads.

Run `php tools/assets/audit-storefront-media.php` from the repository root to verify required demo records exist for every seeded category, product, collection, and hero/mobile/campaign placement, and that seeded banner images/videos, category and collection covers, product thumbnails, product-gallery URLs, public store logo/favicon, and the Open Graph image resolve to files under `api/public/demo-media/`. It also enforces the asset plan's banner (150 KiB), cover (80 KiB), and Open Graph image (150 KiB) byte limits, the admin upload limit and MP4 container signature for demo videos, WebP format and minimum dimensions for banner/cover images, the 16:9 desktop and 4:5 mobile hero ratios, and non-empty alt text for product images, product thumbnails (matched to their gallery image), banners, collection covers, and category images. Customer review-image URLs are validated too; file existence is checked when the public disk is local, while remote storage is reported without making remote reads. It exits with a non-zero status for missing records, files, or failed media checks.

Run `php tools/assets/audit-storefront-api-demo-data.php` to perform a read-only coverage audit of the local API database for API-visible store configuration, catalog/home data, the `new` and bestseller product filters, product variants and images, currently scheduled banners and collections, required published CMS pages (`about`, `shipping`, `size-guide`, `contact`, `privacy`, and `terms`), a currently valid checkout coupon/shipping data, newsletter duplicate handling, review states, pending/delivered orders, cancellation/return requests (including seven-day eligibility and synchronized shipment timestamps), customer account fixtures, and province/ward lookup data for every available province. The audit follows the public API's active-state and publication-window filters, reads the configured database and address catalog, and does not create or change records. `CatalogSeeder` provides sample new-arrival flags only when no active product is already marked new, preserving existing merchandising choices.

Run `php artisan db:seed --class=AdminWorkflowDemoSeeder` from `api/` to create idempotent local/testing fixtures for Admin tasks, personal notifications, a paused report schedule, a multi-SKU inventory adjustment voucher and its stock ledger rows, a historical inventory CSV with downloadable error rows, and a ready report-download CSV containing fictional rows. It also creates a retry-safe no-op failed-job fixture and a login-ready `demo.staff@example.test` account. The local staff password is `STORE_DEMO_STAFF_PASSWORD`; the development example is `StoreDemo123!`, which should be replaced with a unique local secret. The seeder is automatically called by `DatabaseSeeder`, exits outside local/testing, does not create active report jobs or dispatch email or push notifications. Its demo voucher adds two stock units to two sample SKUs once; subsequent runs detect the marker and do not change inventory again.

Run `php tools/assets/audit-admin-api-demo-data.php` for a separate read-only audit of Admin/API demo coverage: seeded roles and permissions, super-admin permission assignments, reusable product tags and active products using them, active shipping methods for manual-order entry, inventory for every active published variant, inventory movement history and the multi-SKU adjustment voucher fixture, personal notifications and an inactive report schedule, order items/payments/status history, shipments for delivered orders, the seeded coupon-use discount against its immutable order snapshot, the local Admin task fixture, the retry-safe failed-job fixture, and the ready report-download CSV and private file. It also reports activity-log count for visibility without requiring fabricated log entries. The script reads the configured local database and does not create or change records.

Some tables intentionally stay empty in the demo database: `settings` is served from API defaults until an operator saves overrides; `payment_refunds` has no fixture because the demo order flow is COD-only; backup runs require a real host backup; browser push subscriptions and linked identities require a real user device/provider; passkeys, trusted devices, 2FA challenges, Telegram pairing codes, email-change tokens, invitation tokens, and impersonation sessions are security credentials or short-lived workflow state and must not be fabricated. Customer review photos are accepted through the Storefront review-upload flow, but the demo seeder does not fabricate customer-submitted media; real rows are checked by the media audit when present. Direct permission grants are created only by the permission-review workflow. Revisit these exclusions when the corresponding credentialed integrations or flows are configured.

Run `php tools/assets/generate-storefront-media-review.php` to create `docs/ui-ux/mockups/storefront-assets-review.html`, a local review board for seeded banners/video, category/collection covers, AI demo product photos, the approved A3 mockup layout, and storefront state illustrations. It reads public media metadata from the configured local database and does not modify the database or upload anything.
